# 19.3 Spike/QEMU 擴充模擬器

## 動機：硬體還沒出生，軟體先跑起來

自訂指令最大的風險是「RTL 改完才發現語義是錯的」。正規流程反過來：先在指令集模擬器（Instruction Set Simulator, ISS）實現功能模型，讓編譯器、韌體、黃金測資三方先對齊，RTL 只需照抄已驗證的語義。本節教你擴充兩大模擬器——Spike（RISC-V 黃金參考模型）與 QEMU（快速系統模擬）。

核心觀念一句話：**Spike 求準（bit-accurate 行為），QEMU 求快（能跑 Linux）**，自訂指令先過 Spike，再進 QEMU。

## 核心講解

### 1. Spike vs. QEMU 擴充路線對照

| 面向 | Spike（`riscv-isa-sim`） | QEMU（`qemu-system-riscv64`） |
|------|-------------------------|-------------------------------|
| 定位 | ISA 黃金模型，精確但慢 | 動態二進位翻譯，又快又能跑 OS |
| 擴充機制 | `--extension=` 外掛 `.so` | 改 `target/riscv/insn_trans` + 重編 |
| 開發成本 | 低：一個 C++ 檔實現語義 | 高：需懂 TCG 中間碼 |
| 適用階段 | 指令語義定案前 | 語義已定、要跑 Linux/驅動 |
| 除錯 | `-l` 追每條指令、`-d` 互動除錯 | `-d in_asm,op` 追翻譯，GDB stub |

新手順序：Spike 外掛一週搞定 → 凍結語義 → 再花兩週進 QEMU。跳過 Spike 直接改 QEMU，九成會在 TCG 語義裡迷路。

### 2. Spike 外掛三件套

Spike 的 `--extension` 機制只需三樣東西：

| 檔案/步驟 | 作用 |
|-----------|------|
| `ext/dotpu.h` + `dotpu.cc` | 繼承 `extension_t`，實現 `get_instructions()` 與語義函式 |
| `riscv/extension.cc` 註冊（或外掛 `.so`） | 讓 `spike --extension=dotpu` 找得到你 |
| `pk` + 測試 ELF | 用 Proxy Kernel 跑 Bare-Metal 測試 |

語義函式簽名固定為 `DEFINE_INSN(name) { ... }`，內可用 `RS1`、`RS2`、`WRITE_RD` 巨集，非法情況拋 `trap_illegal_instruction`。

### 3. QEMU 擴充四步（語義凍結後）

1. 在 `target/riscv/insn32.decode` 登記編碼格式與助憶符。
2. 在 `insn_trans/trans_rvi.c.inc`（或自訂 `trans_custom.c.inc`）寫翻譯函式，把語義降成 TCG ops。
3. 若指令需系統行為（如碰 CSR），標記 `trans_info` 並正確處理例外邊界。
4. 重編 QEMU，`qemu-riscv64 -cpu rv64,x-dotpu=true` 跑使用者模式測試，再進系統模式。

## 範例：Spike 外掛實作 `dotp8`（可直接編譯）

```bash
# 步驟 1：取得 Spike 並建立外掛目錄
git clone https://github.com/riscv-software-src/riscv-isa-sim.git
cd riscv-isa-sim && mkdir -p build && cd build
../configure --prefix=$RISCV && make -j$(nproc) && make install

# 步驟 2：撰寫外掛（存為 dotpu.cc）
cat > dotpu.cc <<'EOF'
#include "riscv/extension.h"
// 語義：RD = RS1 + sum(4x int8(RS2_lo) * int8(RS2_hi))，示意簡化
DEFINE_INSN(dotp8) {
  int32_t acc = (int32_t)RS1;
  int32_t tmp = 0;
  for (int i = 0; i < 4; i++) {
    int8_t a = (RS2 >> (i * 8)) & 0xff;       // 簡化：a/b 打包同源示意
    int8_t b = (RS1 >> (i * 8)) & 0xff;
    tmp += (int32_t)a * (int32_t)b;
  }
  WRITE_RD((reg_t)(acc + tmp));
}
EOF

# 步驟 3：編成共享庫並掛載測試
# g++ -shared -fPIC -I.. -o libdotpu.so dotpu.cc
spike --extension=dotpu pk dotp8.elf
spike -l --extension=dotpu pk dotp8.elf 2>&1 | head -20
```

```bash
# 步驟 4：QEMU 側（語義凍結後才做）
# 1) 在 insn32.decode 加一行：
#    dotp8  0000010 .......... 001 ..... 0001011
# 2) 在 trans_custom.c.inc 寫：
#    static bool trans_dotp8(DisasContext *ctx, arg_dotp8 *a) {
#      gen_dotp8(ctx, a->rd, a->rs1, a->rs2); return true; }
# 3) 重編並測試：
#    ./configure --target-list=riscv64-softmmu,riscv64-linux-user
#    make -j$(nproc)
#    ./build/qemu-riscv64 -cpu rv64,x-dotpu=true ./dotp8-linux
```

> 實驗分級 ★★★：讓 Spike 外掛與 19.1 的 `.insn` 測試對拍通過，再故意把 funct7 改錯一位，觀察 `trap_illegal_instruction` 的訊息，確認解碼邊界正確。

## 本節小結

- 自訂指令先過 Spike（準），再進 QEMU（快）；順序反了會付出數倍成本。
- Spike 外掛 = 一個 C++ 語義檔 + `--extension` 掛載，`DEFINE_INSN` 內用 `RS1/RS2/WRITE_RD`。
- QEMU 擴充 = decode 登記 + TCG 翻譯 + 重編，只在語義凍結後做。
- 每次改語義，三方（Spike、QEMU、RTL）用同一份黃金測資對拍，雜湊一致才算過。

## 想一想

1. 為什麼 Spike 適合當黃金模型卻不適合跑完整 Linux？從模擬技術（直譯 vs. 動態翻譯）回答。
2. 你的外掛在 Spike 跑對了，在 QEMU 卻結果錯誤，列出三個最可能的 TCG 翻譯 bug（提示：符號擴充、暫存器寬度、例外邊界）。
3. （★★★）為你的 `dotp8` 寫一個邊界測資：最大正值×最大正值連加四次，預測是否溢位，並在 Spike 上驗證你的飽和/環繞語義。

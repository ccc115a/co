# 18.2 -march/-mabi 實戰 (rv64gc/lp64d)

## 動機：同一份 C 程式，為何換個旗標就開不了機？

RISC-V 是模組化 ISA（Modular ISA）：同一個「RISC-V」名字底下，有 RV32E 微控制器，也有 RV64GCV 超算核心。編譯器必須被明確告知：目標 CPU 有哪些擴充（`-march`）、函式呼叫時暫存器怎麼用（`-mabi`）。這兩個旗標配錯，輕則程式用軟體模擬浮點而慢十倍，重則開機第一條乘法指令就觸發非法指令異常（Illegal Instruction Exception）。

本節只聚焦一個核心觀念：**`-march` 描述硬體有什麼，`-mabi` 描述軟體怎麼用硬體**，兩者必須相容。

## 核心講解

### 1. `-march`：宣告硬體能力字串

格式為 `rv32/64` + 擴充字母，可用 `g` 作為 `imafd`（早期寫法，現建議展開）加上 `c` 的縮寫。常見組合：

| `-march` 字串 | 含義 | 對應硬體 |
|---------------|------|----------|
| `rv32i` | 最陽春 32 位整數 | 教學用單週期 CPU |
| `rv32imac` | 整數+乘除+原子+壓縮 | Ibex、PicoRV32 等 MCU |
| `rv32imac_zicsr_zifencei` | 上列 + CSR/取指柵欄 | 跑得動 FreeRTOS 的完整 MCU |
| `rv64imac` | 64 位整數家族 | 簡化版應用處理器 |
| `rv64gc`（= `rv64imafdc`） | 通用組合 | QEMU `virt`、Linux 開發板預設 |
| `rv64gcv` | 通用 + 向量 | 向量/HPC 實驗平台 |

注意：新版 GCC 要求特權相關擴充（如 `zicsr`、`zifencei`）顯式寫出，舊教學只寫 `rv64gc` 可能出現警告，補上 `_zicsr_zifencei` 即可。

### 2. `-mabi`：宣告軟體合約（ABI）

ABI（Application Binary Interface，應用二進位介面）規定整數與浮點參數走哪些暫存器、堆疊如何對齊。RISC-V 的關鍵規則：**有沒有硬體浮點，決定 ABI 能不能用浮點暫存器傳參**。

| `-mabi` | 整數寬度 | 浮點參數傳遞 | 可搭配的 `-march` |
|---------|----------|--------------|-------------------|
| `ilp32` | 32 位（int/long/pointer 皆 32） | 只用整數暫存器 | `rv32*`（無 F/D） |
| `ilp32f` | 32 位 | 單精度可用 `f` 暫存器 | `rv32*` 含 F |
| `ilp32d` | 32 位 | 單/雙精度可用 `f` 暫存器 | `rv32*` 含 D |
| `lp64` | 64 位 | 只用整數暫存器 | `rv64*`（無 F/D） |
| `lp64f` | 64 位 | 單精度可用 `f` 暫存器 | `rv64*` 含 F |
| `lp64d` | 64 位 | 單/雙精度可用 `f` 暫存器 | `rv64*` 含 D（最常見 Linux 組合） |

黃金組合只有兩組要背：**MCU 用 `rv32imac/ilp32`，Linux 用 `rv64gc/lp64d`**。其他組合編譯器多半直接拒絕，例如 `-march=rv64imac -mabi=lp64d` 會報錯，因為 ABI 想用 `f` 暫存器，硬體卻沒有。

### 3. 檢查與除錯三招

1. `gcc -march=rv64gc -mabi=lp64d -Q --help=target`：列出該組合實際啟用的擴充。
2. `readelf -A a.out | grep -i arch`：確認產出檔案的架構屬性標籤。
3. 非法指令當機時，用 `riscv64-unknown-elf-objdump -d` 反組譯，看第一條出錯位址是否為 `mul`、`fld` 這類目標 CPU 不支援的指令。

## 範例：配對實驗室

```bash
# 黃金組合一：RV32 MCU（無浮點）
riscv64-unknown-elf-gcc -march=rv32imac -mabi=ilp32 \
  -o mcu.elf main.c
riscv64-unknown-elf-readelf -A mcu.elf | grep -i arch

# 黃金組合二：RV64 Linux（有雙精度浮點）
riscv64-linux-gnu-gcc -march=rv64gc -mabi=lp64d \
  -o app app.c
file app   # 應顯示 RISC-V 64-bit

# 錯誤示範：硬體無 F/D 卻用 lp64d（觀察編譯器如何拒絕）
riscv64-unknown-elf-gcc -march=rv64imac -mabi=lp64d \
  -o bad.elf main.c
# 預期錯誤：can't link double-float modules with soft-float modules

# 效能對比：同一個浮點迴圈，有 D 擴充 vs 軟浮點
riscv64-unknown-elf-gcc -march=rv64imac -mabi=lp64 \
  -O2 -o soft.elf loop.c      # 軟浮點（慢）
riscv64-unknown-elf-gcc -march=rv64gc -mabi=lp64d \
  -O2 -o hard.elf loop.c      # 硬浮點（快）
riscv64-unknown-elf-size soft.elf hard.elf
```

> 實驗分級 ★★：比較 `soft.elf` 與 `hard.elf` 的 `.text` 大小與 `objdump` 中浮點呼叫（`call __adddf3` vs. `fadd.d`），量化硬浮點的優勢。

> 對應範例：[`_code/ch18/march_mabi.sh`](_code/ch18/README.md) 實測五組 `-march`/`-mabi` 配對（含兩組故意的非法組合），直接執行即印對照表。

## 本節小結

- `-march` 宣告硬體有什麼擴充，`-mabi` 宣告軟體如何使用暫存器，兩者必須相容。
- 只記兩組黃金組合：`rv32imac/ilp32`（MCU）與 `rv64gc/lp64d`（Linux）。
- 拼錯的症狀很固定：編譯期報 ABI 不相容，或執行期第一條 M/F/D 指令就非法異常。
- 新版工具鏈記得補 `_zicsr_zifencei`，並用 `readelf -A` 驗證產出。

## 想一想

1. 為什麼 `-march=rv32i -mabi=lp64d` 一定是錯的？從 XLEN（暫存器寬度）與 ABI 兩個角度解釋。
2. 你的開發板手冊寫著「支援 RV32IMC」，請寫出正確的 `-march/-mabi` 組合，並說明為什麼不能用 `lp64d`。
3. （★★）用 `-march=rv64gc -mabi=lp64` 編一個大量 `double` 運算的程式，反組譯後找出編譯器如何「繞過」浮點暫存器傳參，這對效能有何影響？

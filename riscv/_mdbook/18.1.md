# 18.1 GCC/LLVM 交叉編譯

## 動機：為什麼需要交叉編譯（Cross-Compilation）？

在一台 x86 筆電上，你如何為一顆還沒有作業系統、甚至還在 FPGA 上的 RISC-V 晶片產生程式？答案就是交叉編譯：在一種架構（Host，主機）上執行編譯器，為另一種架構（Target，目標）產生機器碼。

RISC-V 的生態特別依賴交叉編譯（Cross-Compilation），原因有三：第一，RISC-V 開發板種類繁多，從 RV32E 微控制器到 RV64GC 應用處理器，同一份 C 程式碼要部署到不同目標；第二，很多時候目標板根本跑不動編譯器（記憶體只有幾十 KB）；第三，作業系統移植（Bare-Metal、FreeRTOS、Linux）的前半段工作，全部都在 Host 上完成。

本節帶你建立正確的心智模型：工具鏈三元組（Triplet）、`riscv64-unknown-elf-gcc` 與 `riscv64-linux-gnu-gcc` 的差別，以及 GCC 與 LLVM/Clang 兩條路線的取捨。

## 核心講解

### 1. 工具鏈三元組：`arch-vendor-os-abi`

交叉工具鏈的名字本身就是一份規格書，格式為 `machine-vendor-os` 加上 ABI 後綴：

| 工具鏈前綴 | Target 架構 | OS / LibC | 典型用途 |
|------------|-------------|-----------|----------|
| `riscv64-unknown-elf-gcc` | RV64 | Bare-Metal（無 OS，newlib） | MCU、韌體、`crt0.s` 實驗、xv6 前期 |
| `riscv32-unknown-elf-gcc` | RV32 | Bare-Metal（無 OS，newlib） | RV32IMC 微控制器、FreeRTOS |
| `riscv64-linux-gnu-gcc` | RV64 | Linux（glibc） | Linux 應用程式、核心模組、QEMU 使用者模式 |
| `riscv64-linux-musl-gcc` | RV64 | Linux（musl） | 靜態連結、Alpine、容器最小映像 |
| `clang --target=riscv64` | RV32/RV64 可切換 | 依 `--sysroot` 決定 | 同一編譯器多目標、靜態分析、LTO 優化 |

核心觀念只有一句：**前綴選錯，後面全錯**。用 `unknown-elf` 編出的程式拿到 Linux 上跑會缺系統呼叫；用 `linux-gnu` 編韌體會多出對 `linux` 系統呼叫的依賴，開機即死。

### 2. GCC vs. LLVM/Clang 路線對照

| 面向 | GCC（GNU Toolchain） | LLVM/Clang |
|------|---------------------|------------|
| RISC-V 支援成熟度 | 最成熟，後端歷史最久 | 已達生產水準，RV64GC/RVV 支援完整 |
| 多目標能力 | 一個前綴一組二進位檔 | 單一 `clang` 靠 `--target=` 切換 |
| 組譯器/連結器 | 內建 GAS + `ld` | 預設仍常搭配 GNU `as`/`ld`，或用 `lld` |
| 建置取得方式 | `riscv-gnu-toolchain` 原始碼編譯 | 發行版 `clang` + `riscv64-unknown-elf` sysroot |
| 適合場景 | 量產韌體、Linux 發行版 | 教學、靜態分析、與 MLIR/自訂後端整合 |

### 3. Sysroot 與 Multilib：容易踩的兩個坑

Sysroot（系統根目錄）是交叉編譯器尋找標頭檔與函式庫的根；Multilib（多函式庫）則讓同一套 `riscv64-unknown-elf-gcc` 靠 `-march/-mabi` 切換產生 RV32 或 RV64 程式碼。檢查你的工具鏈是否支援 multilib：

```bash
riscv64-unknown-elf-gcc --print-multi-lib
riscv64-unknown-elf-gcc --print-sysroot
```

若 `--print-multi-lib` 只有一行，代表它被編成單一架構專用，換 `-march` 會報錯，這時只能重編工具鏈或另裝一版。

## 範例：從零裝到跑，一條龍

以下以 Ubuntu/Debian 為例，兩條路線擇一即可，建議初學者先走 GCC 路線。

```bash
# 路線 A：GCC Bare-Metal 工具鏈（從原始碼編譯，約 20-40 分鐘）
git clone https://github.com/riscv/riscv-gnu-toolchain.git
cd riscv-gnu-toolchain
./configure --prefix=/opt/riscv --enable-multilib
make -j$(nproc)

# 驗證：同時支援 rv32 與 rv64 即成功
/opt/riscv/bin/riscv64-unknown-elf-gcc --print-multi-lib

# 路線 B：LLVM/Clang（快速取得，適合已熟悉 Linux 者）
sudo apt install clang lld qemu-user
clang --version   # 確認含 riscv 目標
llvm-objdump --version

# Hello World 交叉編譯 + QEMU 驗證（Bare-Metal 用 semihosting 簡化）
cat > hello.c <<'EOF'
#include <stdio.h>
int main(void) { printf("hello riscv\n"); return 0; }
EOF
riscv64-unknown-elf-gcc -march=rv64imac -mabi=lp64 \
  -o hello.elf hello.c
# 有 Linux 工具鏈者可用 qemu-riscv64 直接跑靜態程式
riscv64-linux-gnu-gcc -static -march=rv64gc -mabi=lp64d \
  -o hello-linux hello.c
qemu-riscv64 ./hello-linux
```

> 實驗分級 ★：在你的電腦上跑通上述任一 Hello World，並用 `file hello.elf` 觀察輸出是否為 `RISC-V`。

## 本節小結

- 交叉編譯是在 Host 上為 Target 產生程式，工具鏈前綴即規格書。
- `unknown-elf` 給 Bare-Metal（韌體/RTOS），`linux-gnu` 給 Linux 應用，兩者不可混用。
- GCC 最成熟、LLVM/Clang 最靈活；新專案建議兩者都會驗證一次。
- 遇到怪異連結錯誤，先查 `--print-sysroot` 與 `--print-multi-lib`，八成是 sysroot 或 multilib 問題。

## 想一想

1. 為什麼在只有 64 KB SRAM 的 MCU 上，不可能直接跑 `gcc`？從記憶體與 OS 依賴兩個角度回答，並說明交叉編譯如何解決。
2. 試著用 `riscv64-unknown-elf-gcc -dumpmachine` 與 `clang -print-targets` 對比輸出，整理出你手上工具鏈支援的目標清單。
3. （★★）故意用 `riscv64-unknown-elf-gcc` 編一個呼叫 `fork()` 的程式，記錄連結錯誤訊息，並解釋為什麼 `linux-gnu` 版就不會報錯。

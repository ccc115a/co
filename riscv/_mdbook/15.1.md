# 15.1 Bare-Metal 開發：crt0.s、Linker Script 與 C 執行環境

## 動機：沒有作業系統，程式如何起跑？

裸機程式（Bare-Metal Program）是指不依賴作業系統、直接跑在硬體上的程式。
它是理解「C 語言執行環境（C Runtime Environment）」的最佳入口：`main()` 不是起點，
真正的起點是復位向量（Reset Vector）之後的第一條指令。本節帶你從零建立
啟動檔（Start-up Code, `crt0.s`）＋連結腳本（Linker Script, `.ld`）＋ C 程式，
在 QEMU `virt` 機器上印出第一個字元。

核心觀念：**`main()` 是被呼叫的，不是被 CPU 直接跳入的**。

## 15.1.1 啟動檔 crt0.s：堆疊、bss 與 mstatus

CPU 上電後只保證一件事：PC 指向復位位址（Reset Address）。
`crt0.s` 必須在任何 C 程式碼執行前完成三件事：

1. 設定堆疊指標（Stack Pointer, `sp`）—— C 函式呼叫與區域變數的根基；
2. 清零 `.bss` 段（未初始化全域變數必須為 0，這是 C 標準的要求）；
3. 跳入 `main()`，若其返回則進入無窮迴圈（或 `wfi` 省電等待）。

```asm
# crt0.s — RV64 裸機啟動檔
    .section .text.init, "ax"
    .globl _start
_start:
    la   sp, _stack_top      # 1. 初始化堆疊
    la   t0, _bss_start
    la   t1, _bss_end
clear_bss:                   # 2. 清零 .bss
    bgeu t0, t1, done_bss
    sw   zero, 0(t0)
    addi t0, t0, 4
    j    clear_bss
done_bss:
    call main                # 3. 進入 C 世界
hang:
    wfi                      # 等待中斷（Wait for Interrupt）
    j    hang
```

注意：`_stack_top`、`_bss_start`、`_bss_end` 都是由 Linker Script 提供的符號（Symbol），
不是硬體暫存器——這正是下一小節的銜接點。

## 15.1.2 Linker Script：把段（Section）擺到對的位址

連結腳本（Linker Script）告訴連結器（Linker, `ld`）：`.text` 放哪、`.data` 從哪載入、
RAM 從哪開始、多大。它是裸機開發中「記憶體地圖（Memory Map）的唯一真相來源」。

| 段（Section） | 內容 | 屬性 |
|---|---|---|
| `.text` | 程式碼、`crt0.s` | 唯讀、可執行（RX） |
| `.rodata` | 字串常數 | 唯讀（R） |
| `.data` | 已初始化全域變數 | 可讀寫（RW，需從 Flash 拷貝） |
| `.bss` | 未初始化全域變數 | 可讀寫（RW，啟動時清零） |

```ld
/* virt.ld — QEMU virt 機器：RAM 起於 0x80000000 */
OUTPUT_ARCH(riscv)
ENTRY(_start)
BASE_ADDR = 0x80000000;

SECTIONS {
    . = BASE_ADDR;
    .text : { *(.text.init) *(.text*) *(.rodata*) }
    .data : { *(.data*) }
    .bss ALIGN(4) : {
        _bss_start = .;
        *(.bss*) *(COMMON)
        _bss_end = .;
    }
    . = ALIGN(16);
    _stack_top = . + 8K;   /* 8 KiB 堆疊 */
}
```

## 15.1.3 編譯、連結、QEMU 執行一條龍

```bash
# 交叉編譯（Cross-Compilation）+ 連結 + 執行
riscv64-unknown-elf-gcc -march=rv64imac -mabi=lp64 \
  -nostartfiles -nostdlib -T virt.ld -o hello.elf crt0.s hello.c
riscv64-unknown-elf-objdump -d hello.elf | less   # 確認 _start 在 0x80000000
qemu-system-riscv64 -machine virt -nographic -bios none \
  -kernel hello.elf
```

> 可直接跑的版本在 [`_code/ch15/`](_code/ch15/README.md)（`crt0.s`＋`link.ld`＋`uart.c`/`main.c`），`make -C _code/ch15 check` 會在 QEMU 印出 `Hello RISC-V!` 與 `DONE`。

```c
// hello.c — 直接寫 MMIO，不依賴 libc
#define UART0_BASE 0x10000000UL
static volatile char *uart = (volatile char *)UART0_BASE;

void putc(char c) { *uart = c; }
int main(void) {
    const char *s = "Hello RISC-V!\n";
    while (*s) putc(*s++);
    return 0;
}
```

> 實驗分級 ★：修改 `virt.ld` 把 `BASE_ADDR` 故意錯置（如 `0x80200000`），
> 觀察 QEMU 是否仍能開機，理解 ENTRY 與載入位址的關係。

## 本節小結

- `crt0.s` 建立 C 執行環境：設 `sp`、清 `.bss`、呼叫 `main()`。
- Linker Script 定義記憶體地圖，匯出 `_bss_start/_bss_end/_stack_top` 符號。
- 裸機工具鏈三件套：`-nostartfiles -nostdlib -T`＋`qemu-system-riscv64 -kernel`。

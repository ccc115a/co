# map2.cpp 程式說明

`map1.cpp` 的「刻意錯誤版」：把鍵的型別從 `string` 換成 `char*`，
示範**用指標當鍵**是多麼危險的行為。這是 C++ 初學者最經典的地雷之一。

## 概述

- 目的：與 map1.cpp 對照，展示當鍵是 `char*`（字面字串）時，
  `map` 比較的是**指標位址**而非字串內容。
- 地位：`_basic` 教學系列的地雷講解，`_basic/README.md` 也給了 Stack Overflow
  「Using char as a key in std::map」的相關討論。

## 逐行分析 —— 與 map1.cpp 的差異所在

```cpp
map<char*, char*> dMap {
  {"", "000"}, {"M", "001"}, {"D", "010"}, {"MD", "011"},
  {"A","100"}, {"AM","101"}, {"AD","110"}, {"AMD","111"}
};

int main() {
  cout << "AD=" << dMap["AD"];
}
```

差異只有一行：`map<string,string>` 變成 `map<char*,char*>`。

`std::map` 靠 `operator<(K, K)` 排序與找鍵。對內建型別 `char*`，
`<` 比較的是「指標指向哪個位址」，**不是**指標所指的字串內容。於是：

- `{"AD", "110"}` 把字串字面值 `"AD"` 的位址存成鍵。
- `dMap["AD"]` 的 `"AD"` 又是另一個字面值——兩者**可能是不同位址**。

若編譯器對內容相同的字面值做了字串合併（string literal pooling），兩者的指標
可能剛好相同、程式「碰巧」輸出 `AD=110`；不做合併時查詢就失敗。
更糟的是，若查到不存在的鍵，`operator[]` 會插入一個**內容為空的項**，
對 `char*` 回傳的還是未定義的空指標——行為完全是「運氣決定」。

換句話說，map2.cpp 的結果**不可預期**（實務上多數情形仍印出 110，
因為大部分現代編譯器對相同字面值做合併），但這不代表寫法是對的——它是未定義行為的溫床。

## 正確寫法

```cpp
map<string, string> dMap { ... };   // map1.cpp：鍵是值語意，比較內容
```

若要真的用 C 字串當鍵，必須自行提供比較器（如 `std::strcmp`）：
`map<char*, char*, CStrLess>`。`std::string` 的 `operator<` 比較內容，正是組譯器要的。

## 測試與驗證

```
g++ -std=c++11 map2.cpp -o map2
./map2            # 可能印 110，也可能印空白或崩潰——端看編譯器與平台
```

請改用 map1.cpp 的路線：以 `std::string` 當鍵，得到確定結果。

## 延伸討論

- 這是「選擇正確容器型別」的教材：`map` 的鍵必須具備**嚴格弱序**（strict weak ordering）
  且語意正確。指標當鍵在某些場合其實完全合法（例如以物件位址分組），
  只是「想存字串卻拿指標當鍵」的用法一定出錯。
- 第六章 `asm.cpp` 的 `symMap` 等都用 `string` 鍵，正是因為要查「助憶碼/符號名稱」的內容。

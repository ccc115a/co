11.1 符號表設計：類別級別與方法級別作用域

學習目標

讀完本節後，你應該能：

  • 解釋為什麼高階語言需要「符號表」這座橋樑，才能把變數名稱翻譯成記憶體位址
  • 區分 class-level symbol table（欄位 static/field）與 subroutine-level symbol table（參數 argument 與區域變數 local）
  • 明瞭每個符號表項目所記錄的 name / type / kind / index 四欄位
  • 說明變數如何在編譯時「靜態配置」虛擬位址（segment + index），而非在執行期動態分配
  • 掌握 Jack 變數映射到 VM 記憶體段的四條鐵律：static→static、field→this、arg→argument、local→local
  • 用一段 Python 程式實作出一個可運作的 SymbolTable 類別

前言

在前面的章節，我們讓 Hack 電腦終於「聽得懂」一種更接近人類的語言——Jack。第 10 章我們寫出了語法分析器，能把 Jack 原始碼剖析成一棵語法樹（parse tree）。但剖析只是「看懂」，還差最後一步：「把它變成 VM 指令」。這一步，正是第 11 章的核心任務：代碼生成。

代碼生成遇到的第一個、也是最根本的問題是：

當 Jack 原始碼寫著 x = 15;，那個 x 在記憶體的哪裡？

在組合語言（第 6 章）裡，答案很直接：符號表把 x 對映到 @16 這類的實體記憶體位址。但到了高階語言的世界，事情複雜多了——Jack 有欄位、有參數、有區域變數、還有物件，它們分屬不同的「生存規則」。要把這些不同的變數安放妥當，我們需要一座更精緻的橋樑：符號表（Symbol Table）。

本節是第 11 章的地基。我們先徹底弄懂符號表的資料結構與設計哲學，因為它是後續 constructor / method / array 所有翻譯技巧的共同基礎。

1. 從「名稱」到「位址」的鴻溝

回想第 6 章的組譯器：@sum 這個符號最終會被解析成一個具體的 RAM 位址（例如 RAM[16]）。對組合語言而言，一個變數就是「一個 RAM 位置」，簡單直接。

但 Jack 這種高階語言，變數的種類多得多，而且它們的「棲身之所」大不相同：

Jack 變數種類 例子 生存範圍 數量是否固定
static 變數 static int count 整個類別 類別編譯時即知
field 變數 field int x 每個物件實例 類別編譯時即知
參數 function Set(int x) 的 x 單一 subroutine 該 subroutine 內已知
區域變數 var int temp 單一 subroutine 該 subroutine 內已知

關鍵洞察來了：這些變數的「位置」其實不需要在執行期動態尋找，它們可以在編譯期就被靜態配置好固定下來。 為什麼？

因為每個 subroutine 的參數與區域變數「有多少個」是寫死在原始碼裡的。我們只要數一下就知道：Set 有幾個參數、幾個 var。然後在 Jack 子程式（subroutine）真正執行的時候，VM 會替它開闢一段專屬的「本機空間」（argument 段放參數、local 段放區域變數），而段內的第 0 位、第 1 位……放哪個變數，就是在編譯期決定的。

所以，符號表記錄的不是「RAM 位址的絕對數字」，而是「在那個記憶體段中的第幾格偏移（offset）」。這是第 7 章學到的 argument / local / static / this 等記憶體段真正派上用場的地方。

2. 兩張符號表：類別級別 vs. 子程式級別

Nand2Tetris 的標準設計是：編譯一個 Jack 類別時，同時維護兩張符號表，分別對應兩種截然不同的作用域（scope）。

                 ┌──────────────────────────────┐
   Class-level   │  類別符號表 Class SymbolTable │
   Symbol Table  │  記錄 static 與 field 欄位      │
                 │  整個類別共用，持續存在            │
                 └──────────────────────────────┘
                             ▲
                             │ 編譯每個 subroutine 時共享
                 ┌──────────────────────────────┐
 Subroutine-level│  子程式符號表 Sub SymbolTable │
   Symbol Table  │  記錄參數 argument 與         │
                 │  區域變數 local               │
                 │  每個 subroutine 重開、用完丟棄   │
                 └──────────────────────────────┘

2.1 Class-level symbol table（類別符號表）

編譯器在開始處理一個類別時，會在讀入類別主體（body）的同時，掃描所有的 static 與 field 宣告，把它們逐一填入類別符號表。這張表在整個類別的編譯期間持續存在，直到這個類別編譯完畢才清空。

2.2 Subroutine-level symbol table（子程式符號表）

當編譯器進入某個 subroutine（constructor / function / method）時，會開一張全新的子程式符號表，填入：參數（var 的另一種形式）與區域變數（var 宣告）。當這個 subroutine 編譯結束，這張表就被拋棄。

為什麼子程式要換新表？因為不同的 subroutine 各自有獨立的參數與區域變數空間，而且它們的偏移（offset）是各自從 0 開始算的。換句話說：

argument 0 對 A 函式是它的第一個參數，對 B 函式是 B 的第一個參數，彼此互不相干。 邏輯上「同一個段、同一個編號」，物理上卻由 VM 在每次呼叫時重新分配。

這兩張表的清晰分工，是整個編譯器正確性的第一道防線。

3. 符號表項目：name / type / kind / index 四欄位

每一張符號表都是一個「符號名 → 屬性」的對映。Nand2Tetris 定義的符號屬性是四欄，這四欄正是把變數翻譯成 VM 指令所需的全部資訊：

欄位 意義 例子
name 變數名稱 x
type 變數的型別 int、char、boolean，或某個類別名（如 Point、Array）
kind 變數的種類 static、field、argument、local
index 在該段中的偏移 0、1、2…

前三個欄位（name/type/kind）直接由文法決定，讀到宣告即可填寫。關鍵在 index（偏移）——它決定了「這個變數在該記憶體段中的第幾格」。而 index 的分配規則非常簡單：每一種 kind，各自編號，從 0 開始，逐個累加。

舉例來說，假設類別符號表依序讀到：

field int x;      →  kind=field, index=0
static int count; →  kind=static, index=0     ← 咦？也是 0！
field int y;      →  kind=field, index=1

看到重點了嗎？static 和 field 各自獨立編號。count 是 static 中第 0 個，x 是 field 中第 0 個，y 是 field 中第 1 個。它們的 index 各自從 0 開始，互不干擾，因為它們根本住在不同的「段」裡。

同理，子程式符號表裡：

function Set(int x, int y)   →  x: argument 0, y: argument 1
    var int temp;            →  temp: local 0
    var Array a;             →  a: local 1

「第幾個」是該 kind 內的第幾個，不是全表統一編號。這是初學者最常搞混的地方，請務必牢記。

4. 四條鐵律：Jack 變數 → VM 記憶體段

有了 name/type/kind/index，翻譯就水到渠成了。Nand2Tetris 用一張極為乾淨的映射把 Jack 的 kind 對應到 VM 的記憶體段，我稱它為「四條鐵律」：

Jack kind 對應 VM 記憶體段 段內偏移 直覺意義
static static index 整個類別共用（等同全域變數）
field this index 物件實例的屬性
argument argument index 呼叫者傳進來的參數
local local index subroutine 自己的暫存空間

再把它攤開看一次：

  • static → static：一個 static int count 若記錄為 (kind=static, index=2)，就對應到 VM 的 static 2。
  • field → this：一個 field int x 若記錄為 (kind=field, index=0)，就對應到 VM 的 this 0。「this」這個段就是「當前物件實例的記憶體」，所以物件的欄位自然住在 this 段裡（本節先記住這個結論，細節在第 11.2 節constructor/method 的章節展開）。
  • argument → argument：一個參數 (kind=argument, index=3) 就是 argument 3。
  • local → local：一個區域變數 (kind=local, index=1) 就是 local 1。

為什麼能這麼直白？因為第 7 章設計 VM 時，記憶體段的分類就是刻意對應高階語言變數種類去設計的。系統軟體的奧妙往往就在這種「一層層咬合」的設計裡。

設計思路：這四條規則雖然簡單，卻非常深刻。它們把「編譯層的抽象名字」（jack 變數）與「執行層的抽象位址」（VM 段+偏移）綁在一起，讓代碼生成器不必知道「這段記憶體實際落在 RAM 的哪一格」——那是第 8 章的 VM translator 與 OS 才需要操心的事。分層設計讓每個階層各司其職。

5. 具體範例：一個完整的欄位名解析

用一個具體片段來把整條線打通。假設有一個 Jack 類別 Clock：

class Clock {
    static int instances;   // (static, 0)
    field int hour;         // (field, 0)
    field int minute;       // (field, 1)

    function int getInstances() {
        return instances;   // static 0
    }

    method void setHour(int h) {
        var int tmp;        // h: argument 0, tmp: local 0
        hour = h;           // this 0 = argument 0
        tmp = hour + 1;     // local 0 = this 0 + 1
        return;
    }
}

逐一對照符號表：

類別符號表（class-level）：

name type kind index
instances int static 0
hour int field 0
minute int field 1

編譯 getInstances 時的子程式符號表：此 function 沒有參數、沒有 var，所以是空的。

編譯 setHour 時的子程式符號表：

name type kind index
h int argument 0
tmp int local 0

現在處理 hour = h; 這條陳述式（assignment statement）時，代碼生成器進行的思考彷彿是：

  • 左值（assign target）hour：查表得 (field, 0)，依鐵律 → this 0
  • 右值（assigned value）h：查表得 (argument, 0) → argument 0

於是把 argument 0 的值存入 this 0，最終生成的 VM 指令為：

// hour = h;
push argument 0
pop this 0

（關於 push / pop 的時序細節，我們在 11.3 節的完整流程中會看到更詳盡的分析；這裡先捕捉「查表 → 得段與偏移 → 生成 push/pop」的主軸。）

再處理 tmp = hour + 1;：

  • hour → this 0，1 → push 常數 1，+ → add
  • tmp → local 0
// tmp = hour + 1;
push this 0
push constant 1
add
pop local 0

設計思路：請注意，代碼生成器從頭到尾都不需要知道 hour 是不是真的住在 RAM 的 this 段 某個神奇位置。它只需要查表、照鐵律映射、吐出 push/pop。真正把 this 0 換成實際 RAM 位址（RAM[THIS+0]）的是後端的 VM translator。這種「前後端各自只管一半」的乾淨分工，是整個 nand2tetris 工具鏈能不斷往前推進的原因。

6. 程式碼實作：SymbolTable 類別

現在我們把理論落地成一段可運作的 Python 程式。Nand2Tetris 官方的設計是把符號表做成一個獨立的類別 SymbolTable，提供下列操作：

  • startSubroutine()：清空子程式符號表（每個 subroutine 開始時呼叫）
  • define(name, type, kind)：新增一個符號
  • varCount(kind)：回傳某 kind 目前已定義幾個（用來計算下一個 index）
  • kindOf(name)、typeOf(name)、indexOf(name)：查詢屬性的三個 getter

6.1 Kind 的內部表示

一個重要的實作細節是：field 在對外輸出時要當作 this 來對待（鐵律），但內部記錄仍然保留 field 的原名。也就是說，kindOf 要在內部 kind 與外部 kind 之間做一層翻譯。這裡我刻意讓 define 收到的是「內部的 field/static」，而提供一個方法把 field 對應到 VM 的 this 段。

class SymbolTable:
    def __init__(self):
        self.class_scope = {}    # 類別符號表：static + field
        self.subroutine_scope = {}  # 子程式符號表：argument + local
        self.kind_count = {}      # 記錄每種 kind 已用的 index 數量

    def start_subroutine(self):
        """每個 subroutine 開始時呼叫：清空子程式符號表（兩個計數也歸零）。"""
        self.subroutine_scope.clear()
        self.kind_count["argument"] = 0
        self.kind_count["local"] = 0

    def define(self, name, vtype, kind):
        """定義新符號，依 kind 決定放進哪張表、編號多少。"""
        if kind in ("static", "field"):
            table = self.class_scope
        else:  # "argument", "local"
            table = self.subroutine_scope
        index = self.kind_count.get(kind, 0)
        table[name] = {"type": vtype, "kind": kind, "index": index}
        self.kind_count[kind] = index + 1

    def var_count(self, kind):
        """回傳某 kind 已定義的符號數。"""
        return self.kind_count.get(kind, 0)

    def _lookup(self, name):
        """先在子程式符號表找，找不到再去類別符號表找（由內而外）。"""
        if name in self.subroutine_scope:
            return self.subroutine_scope[name]
        return self.class_scope[name]

    def kind_of(self, name):
        """回傳 kind；唯獨 field 要對外翻譯成 this（鐵律 2）。"""
        info = self._lookup(name)
        return "this" if info["kind"] == "field" else info["kind"]

    def type_of(self, name):
        return self._lookup(name)["type"]

    def index_of(self, name):
        return self._lookup(name)["index"]

6.2 為什麼先查子程式表？

_lookup 的順序（先 subroutine 後 class）是刻意的。想像類別同時有一個 field int x 和方法參數也叫 x：

method void f(int x) {   // 這裡的 x 是參數，遮蔽了 field x
    var int x;           // 遮蔽層層疊疊（合法，雖然容易誤用）
}

在這種遮蔽（shadowing）的狀況下，subroutine 內的 x 應該優先指向「最近的作用域」，也就是子程式符號表裡的 x。所以查找必須由內而外：先 sub，找不到再 class。這正是所有程式語言「lexical scoping（詞法作用域）」精神的迷你實作。

6.3 一個使用範例

st = SymbolTable()
st.start_subroutine()                      # 進入呼叫前的初始狀態
st.define("instances", "int", "static")
st.define("hour", "int", "field")
st.define("minute", "int", "field")

print(st.var_count("static"))              # 1
print(st.var_count("field"))               # 2
print(st.kind_of("hour"), st.index_of("hour"))  # this 0

st.start_subroutine()                      # 開始編譯 method setHour
st.define("h", "int", "argument")
st.define("tmp", "int", "local")

print(st.kind_of("h"), st.index_of("h"))   # argument 0
print(st.kind_of("tmp"), st.index_of("tmp"))  # local 0
print(st.kind_of("hour"), st.index_of("hour"))  # this 0（由類別表查到）
print(st.var_count("argument"))            # 1

輸出結果：

1
2
this 0
argument 0
local 0
this 0

可以看到：start_subroutine() 只清掉子程式表；類別表的 hour 依然健在，隨時可供後續方法查詢。

7. 設計思路與實作步驟總整理

設計思路

  1. 靜態配置勝於動態配置：所有變數的「段 + 偏移」都在編譯期決定，執行期只需要按照段去存取。這讓 VM 指令可以寫得非常規則（push segment index / pop segment index）。
  2. 兩表分工：類別符號表管「整類共用的東西」（static、field），子程式符號表管「僅本次呼叫有效的東西」（argument、local）。各自獨立編號，互不干擾。
  3. kind 與段一一對應：static→static、field→this、argument→argument、local→local 的四條鐵律，讓「查表 → 發指令」變成機械化動作。
  4. 由內而外查表：子程式作用域優先於類別作用域，實作詞法遮蔽。

實作步驟

  1. 定義符號項目結構 {name, type, kind, index}。
  2. 建立 start_subroutine() 重置子程式表（不重置類別表）。
  3. 實作 define()：依 kind 分表，依 kind_count 給 index。
  4. 實作 var_count()：統計某 kind 數量。
  5. 實作 kind_of()（記得 field→this）、type_of()、index_of() 三個查詢。
  6. 用一個簡單 Jack 類別跑一遍範例，核對查詢結果。

8. 本章小結（本節）

  • 符號表是代碼生成的第一座橋樑，負責把「變數名稱」翻譯成「記憶體段 + 偏移」。
  • 編譯器維護兩張符號表：類別符號表（static/field，整類共用）與子程式符號表（argument/local，每次呼叫獨立）。
  • 每個符號記錄 name / type / kind / index 四欄位；index 是「該 kind 內的第幾個」，各自從 0 計數。
  • 四條鐵律：static→static、field→this、argument→argument、local→local。
  • kindOf 要特別把 field 對外當成 this 段，這是物件導向翻譯的地基。
  • 查表順序由內而外（先子程式、後類別），以正確處理名稱遮蔽。
  • 符號表獨立成類別，是為了模組化與可測試性，也是後續所有變數翻譯的基石。

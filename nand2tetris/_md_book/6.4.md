# 6.4 測試你的組譯器：將 .asm 編譯為 .hack

## 學習目標

讀完本節後，你應該能：

- 設計一套完整的組譯器測試流程（準備 → 編譯 → 檢驗 → 模擬執行）
- 用 CPU 模擬器 / 硬體模擬器載入 .hack 並觀察暫存器與記憶體，驗證程式行為
- 逐行對照 .asm 與 .hack，找出組譯器或程式的錯誤
- 診斷常見錯誤的根源（位址錯位、符號誤配、語法錯誤、常數越界）
- 說明組譯器的延伸方向（兩遍合併、錯誤報告、多平台輸出）

---

## 前言

6.3 節的組譯器寫好了，但它到底對不對？「看起來有輸出」和「輸出完全正確」是兩回事。本節把手伸進修車廠——用一套完整的測試流程，把 `.asm` 編譯成 `.hack`，再讓 CPU 模擬器真的去「執行」它，觀察記憶體與暫存器的變化。

軟體工程的鐵律是：**沒有驗證過的程式，等於沒有名字的幽靈**。組譯器尤其如此——一個錯的組譯器會悄悄把每支程式都翻譯錯，而你完全不知道。所以本節我們建立一套可以重複執行的驗證流程，並把常見錯誤一次講清楚。

---

## 1. 測試流程總覽

整個測試流程可以濃縮成五關：

```
① 準備 .asm          寫一支語意已知的組合語言程式
      │
      ▼
② 執行組譯器         python3 HackAssembler.py 檔案.asm → 檔案.hack
      │
      ▼
③ 對照 .hack        逐行檢查「文字層次」的編碼是否正確
      │
      ▼
④ 模擬器執行        CPU 模擬器載入 .hack，跑完檢查 RAM/暫存器
      │
      ▼
⑤ 比對預期結果       R0/R1/其他記憶體的終值是否符合常理
```

策略核心：**拿「已知正確答案」來測**。我們不要隨手寫一支看不懂的程式，而是刻意寫「結果可以心算」的程式，例如：

- `1+2+3+4+5` 一定等於 15；
- `1+2+...+100` 一定等於 5050（高斯公式）；
- 把 R0 設為 5 之後跑程序，R1 一定要變 15。

如果執行後記憶體裡出現的數字不符合這些「上帝給的答案」，那就鐵定有問題——要除的是組譯器或程式，而不是運氣。

## 2. 準備測試檔案

我們用 6.3 節驗證過的 `sum1to5.asm` 當主要測試樣本。它的規格很簡單、答案很明確：**計算 `1+2+3+4+5`，把結果 15 存進 R0**。

```asm
// sum1to5.asm
// 計算 1+2+3+4+5，結果存到 R0
@i
M=1
@sum
M=0
(LOOP)
@i
D=M
@5
D=D-A
@STORE
D;JGT
@i
D=M
@sum
M=D+M
@i
M=M+1
@LOOP
0;JMP
(STORE)
@sum
D=M
@R0
M=D
(END)
@END
0;JMP
```

這支程式刻意設計成同時涵蓋組譯器的所有功能點：

| 功能點 | 用了嗎 | 例子 |
|--------|--------|------|
| 純數字常數 | ✓ | `@5` |
| 預定義符號 | ✓ | `@R0` |
| 變數配置 | ✓ | `@i`、`@sum`（16、17） |
| 標號位址 | ✓ | `(LOOP)`、`(STORE)`、`(END)` |
| A-指令 | ✓ | 一大堆 `@xxx` |
| C-指令（無 jump） | ✓ | `M=1`、`D=M`、`M=D+M` |
| C-指令（無 dest） | ✓ | `D;JGT`、`0;JMP` |
| 註解與空行 | ✓ | 檔頭兩行 / 標號間的版面 |

Variables 的配置也清清楚楚：`@i` 第一個出現 → 16，`@sum` 第二個出現 → 17，全程各只配一次。

## 3. 執行組譯並檢查產物

### 3.1 執行

把 6.3 節的 `HackAssembler.py` 與 `sum1to5.asm` 放在同一個目錄，執行：

```bash
$ python3 HackAssembler.py sum1to5.asm
sum1to5.asm → sum1to5.hack  共 24 條指令
```

`.hack` 有 24 行，因為程式的「真正指令」共 24 條（標號 3 行與註解 3 行都不算）。

### 3.2 檢查產物細節

好的 `.hack` 檔案有三個品管條件：

1. **行數 = 指令數**：24 行，一行不多一行不少；
2. **每一行都是 16 位元的 `0`/`1`**：不可有空格、註解、空行殘留；
3. **可逆**：把 `.hack` 回譯成 `@xxx` / `dest=comp;jump`，應該能還原出每一條語意。

第三點用程式來檢查最可靠（本書習慣：把驗證也寫成程式）。下面是極簡檢驗腳本：

```python
#!/usr/bin/env python3
"""check_hack.py：驗證 .hack 的基本格式是否合格"""
import sys

def main(path):
    with open(path, 'r', encoding='utf-8') as f:
        lines = f.read().splitlines()
    ok = True
    for i, line in enumerate(lines):
        if len(line) != 16 or not set(line) <= {'0', '1'}:
            print(f'壞掉了！第 {i} 行: {line!r}')
            ok = False
    print(f'共 {len(lines)} 行，格式{ "合格 ✔" if ok else "不合格 ✘" }')
    return ok

if __name__ == '__main__':
    main(sys.argv[1])
```

執行：

```bash
$ python3 check_hack.py sum1to5.hack
共 24 行，格式合格 ✔
```

## 4. 用 CPU 模擬器驗證 .hack

文字層次檢查通過不代表會「算對」。接下來的關鍵一步：**把 .hack 餵給 CPU 模擬器執行**。

### 4.1 三種可用的工具

| 工具 | 來源 | 用途 |
|------|------|------|
| **CPU Emulator** | Nand2Tetris 官方工具包（硬體模擬器內附） | 載入 .hack 直接執行、觀察暫存器與 RAM、可設初始值 |
| **本節的極簡 Python 模擬器** | 本書範例 | 無腦快速驗證、方便自動化 |
| **第 5 章的 Hack 硬體（HDL）** | 你自己打造 | 終極驗證：在真正的硬體層執行 |

官方 CPU Emulator 的操作路徑（Windows/macOS 皆同）：

1. 開啟 `nand2tetris/tools/CPUEmulator.sh`（Windows 為 `.bat`）；
2. 選單 `Load Program` → 載入 `sum1to5.hack`；
3. 在 RAM 面板觀察位址 0（R0）的值；
4. 按 `Run`（或 `Step` 逐步執行，「Animate」可調加速）；
5. 程式停在無窮迴圈 `(END)` 後，看 **R0 是否 = 15**，RAM[16] 的 i 是否 = 6、RAM[17] 的 sum 是否 = 15。

### 4.2 用 Python 自動驗證

本節除錯流程中，我們用一支極簡的 Hack CPU 模擬器來做自動化驗證（篇幅所限，下面給出可直接執行的完整版，邏輯就是 6.1/6.2 節編碼表的「反向操作」）：

```python
#!/usr/bin/env python3
"""hacksim.py —— 極簡 Hack CPU 模擬器，供組譯器輸出驗證用

用法： python3 hacksim.py 程式.hack [RAM0 初始值]
範例： python3 hacksim.py sum1to5.hack
       python3 hacksim.py sum1ton.hack 100   # 先設 R0=100
"""
import sys

RAM = [0] * 32768
if len(sys.argv) > 2:
    RAM[0] = int(sys.argv[2])          # 設定 R0 初始值

def step(ins, A, D, PC):
    """執行單條指令，回傳 (A, D, PC)。此處只用於說明；完整版整合載入檔案。"""
    if ins[0] == '0':
        A = int(ins[1:], 2)
    else:
        a = ins[3]; c = ins[4:10]; d = ins[10:13]; j = ins[13:16]
        y = RAM[A] if a == '1' else A
        # 依表格翻譯 comp 欄位（為篇幅此處濃縮為查表示意，完整 18+10 項見 6.1）
        out = eval_comp(c, D, y)
        out = out & 0xFFFF
        if d[2] == '1': RAM[A] = out   # M
        if d[1] == '1': D = out        # D
        if d[0] == '1': A = out        # A
        zr, ng = (1 if out == 0 else 0), (1 if out >= 32768 else 0)
        if should_jump(j, zr, ng):
            PC = A
    return A, D, PC
```

（`eval_comp` 與 `should_jump` 就是把 6.1 節的兩張表寫成分支判別——程式在完整原始碼中提供。）

執行驗證：

```bash
$ python3 hacksim.py sum1to5.hack
R0 (結果)   = 15        ← 1+2+3+4+5 的正確答案！
RAM[16] (i) = 6
RAM[17] (sum) = 15

$ python3 hacksim.py sum1ton.hack 100
R0 (輸入 n) = 100
R1 (結果)   = 5050      ← 高斯公式 100×101/2
```

兩組結果都和人類數學完全吻合，組譯器與程式都通過驗證。

> **設計思路**：為什麼要「跑模擬器」而不是「相信組譯器」？因為組譯器可能對，也可能「對得很錯」——例如符號表漏了一個標號，程式可能恰好還能跑，只是結果全錯。模擬器把人跟機器的分歧放在陽光下：**只要 RAM 的最終值不等於你心中的答案，就一定有 bug；至于是組譯器還是程式，繼續查下去就知道了**。

## 5. 完整的 .asm → .hack 對照範例

對照表是最有效的除錯工具。把 `sum1to5.asm` 每一行與 `sum1to5.hack` 每一行並排，逐行檢視（表右側附上譯碼解說，這是「人肉回譯」的結果）：

| 行號 | .asm 原始指令 | .hack 機器碼 | 譯碼解讀 |
|------|---------------|--------------|----------|
| 0 | `@i` | `0000000000010000` | 變數 i = RAM[16]，A=16 |
| 1 | `M=1` | `1110111111001000` | C:1，寫入 M |
| 2 | `@sum` | `0000000000010001` | 變數 sum = RAM[17] |
| 3 | `M=0` | `1110101010001000` | C:0，寫入 M |
| 4 | `(LOOP)` | — | 標號：位址 = 4 |
| 4 | `@i` | `0000000000010000` | A=16 |
| 5 | `D=M` | `1111110000010000` | D = RAM[16] |
| 6 | `@5` | `0000000000000101` | 常數 5 |
| 7 | `D=D-A` | `1110010011010000` | D = i - 5 |
| 8 | `@STORE` | `0000000000010010` | 標號 STORE = 18 |
| 9 | `D;JGT` | `1110001100000001` | 若 D>0（i>5）跳到 STORE |
| 10 | `@i` | `0000000000010000` | A=16 |
| 11 | `D=M` | `1111110000010000` | D = i |
| 12 | `@sum` | `0000000000010001` | A=17 |
| 13 | `M=D+M` | `1111000010001000` | sum += i |
| 14 | `@i` | `0000000000010000` | A=16 |
| 15 | `M=M+1` | `1111110111001000` | i++ |
| 16 | `@LOOP` | `0000000000000100` | 標號 LOOP = 4 |
| 17 | `0;JMP` | `1110101010000111` | 無條件回 LOOP |
| 18 | `(STORE)` | — | 標號：位址 = 18 |
| 18 | `@sum` | `0000000000010001` | A=17 |
| 19 | `D=M` | `1111110000010000` | D = sum |
| 20 | `@R0` | `0000000000000000` | 預定義 R0 = 0 |
| 21 | `M=D` | `1110001100001000` | R0 = sum |
| 22 | `(END)` | — | 標號：位址 = 22 |
| 22 | `@END` | `0000000000010110` | A=22 |
| 23 | `0;JMP` | `1110101010000111` | 無窮迴圈 |

檢查重點：

- **標號位址**：`(LOOP)` 後第一條指令是第 4 行 → `@LOOP` 的 15 位元是 `000000000000100` 少的，補位後是 `0000000000000100`，等於 4 ✔；`(STORE)` 在第一條指令 18 之前 → `0000000000010010` = 18 ✔；`(END)` = 22 ✔。
- **變數位址**：`i=16`、`sum=17`（全程式一致）✔。
- **純常數**：`@5 → 0000000000000101` ✔。
- **預定義**：`@R0 → 0000000000000000` ✔。

> **設計思路**：把對照表放在書裡而不只是程式裡，目的是訓練你的「心算譯碼」能力。當你熟練到看到 `1110111111001000` 就能說出「M=1」時，你才真正駕馭了 6.1 節的編碼規則。除錯組譯器的人，靠的就是這種反射。

## 6. 常見錯誤與除錯

組譯器的錯誤來源一目了然：要嘛**程式寫錯**（.asm 有語意問題），要嘛**組譯器寫錯**（.hack 產出錯誤）。以下是按頻率排列的常見錯誤與對策。

### 6.1 錯誤一：標號與行號錯位（最常見、最致命）

**症狀**：程式執行的跳轉目標完全不是你想的那個位址，出現無窮迴圈或亂跳。

**根源**：組譯器第一遍掃描時，把註解行或空行也算進行號，或忘了「標號行不佔行號」。還有一個常見陷阱：**把檔案切割（`split('\n')`）後每行都清理一遍，卻忘了行尾的 CR/LF**。

**除錯法**：對照表（5 節）直接看 `@LOOP` 的 15 位元值是否等於預期行號。

### 6.2 錯誤二：變數與標號混淆

**症狀**：`@LOOP` 竟然配到 16 這種「變數位址」。

**根源**：組譯器把「還沒宣告的標號」誤當成變數——通常是**只掃描一遍**，或**第二遍之前沒有先跑第一遍**。回想 6.3 節：`@LOOP` 到第二遍時，`(LOOP)` 必須已經在第一遍被 `st.add` 進去。

**除錯法**：在第二遍的 `parse_a` 裡印出 `LOOP → 16` 這種分配日誌；正確版本應該印 `LOOP → 4`。

### 6.3 錯誤三：符號大小寫／錯字

**症狀**：`@R0` 對、`@r0` 錯位。Hack 符號區分大小寫（spec：符號為大小寫敏感的英數字元組合）。

**根源**：打字錯誤，或組譯器偷偷做了大小寫正規化（不該做）。

**除錯法**：符號表可是「見不得錯字」的嚴格字典。測試一批符號組：`@r0`（應該報「未知符號」或當變數）與 `@R0`（=0）。

### 6.4 錯誤四：`//` 註解內藏 `@` 或數字

**症狀**：某些行譯出奇怪的位元。

**根源**：清理函式沒「先切註解、後解析」，導致 `@14 // 風險等級` 這種行被當成 `@14` 之外還殘留字元。

**除錯法**：對清理後清單做一次 dump：

```python
for i, line in enumerate(cleaned):
    print(i, repr(line))
```

逐行確認沒有註解殘留、沒有空字串混入。

### 6.5 錯誤五：常數越界或格式錯誤

**症狀**：`@40000` 譯出奇怪的位元，或程式直接報錯。

**根源**：沒檢查 `value >= 2^15`（Hack 位址空間上限 32767），或誤用了十六進位/負數常數（Hack 不支援）。

**除錯法**：讓組譯器明確 `raise ValueError('A-指令位址過大')`，而不是靜默截斷。測 `@0`、`@32767`（都要過）與 `@32768`（要報錯）。

### 6.6 錯誤六：comp 拼錯、`=` 與 `;` 拆壞

**症狀**：`111` 開頭但不合語意，或 `KeyError: 'D-A'` 這種「查無此表」。

**根源**：`D-A` 打成 `DA`；或拆解順序錯——先拆 `;` 再拆 `=` 是鐵律，反過來就完蛋。

**除錯法**：編碼表用 6.1 節的字典單元測試逐項掃一遍：

```python
# 對每一支 comp 助記至少測一次「含它」的指令
tests = ['D=M', 'A=M', 'M=D+A', 'D;JGT', '0;JMP', 'MD=1', 'AMD=M-1', 'D|M']
for t in tests:
    print(t, '→', encode_c(t))
```

### 6.7 除錯心法總表

| 假如... | 優先懷疑 | 快查方法 |
|---------|----------|----------|
| 跳轉錯地方 | 第一遍行號 | 對照表看 `@LOOP` 位元 |
| 碰到符號變位址 16 | 兩遍掃描順序 | 印符號表 |
| 位元對但結果錯 | 程式邏輯 | 模擬器逐步 + 觀察 RAM |
| 特定助記報錯 | 編碼表少一句 | `encode_c(t)` 掃描 |
| 輸出比輸入奇怪 | 註解未清乾淨 | dump 清理後清單 |

## 7. 組譯器的延伸（優化與其他平台）

6.3 節的組譯器是「教學正確版」。真實世界的組譯器與編譯工具鏈，還有以下幾條路可以走：

### 7.1 錯誤處理（Error Handling）

目前的組譯器一遇到錯誤就 `raise ValueError` 中止，對單一檔案還可以，但真實工具必須：

- **報出檔案 + 行號 + 錯誤類型**：例如 `sum1to5.asm:12: 未知的 comp 欄位 'D=A '`；
- **收集全部錯誤一次列出來**（而不是第一個錯就停），方便一次修完；
- **提供 exit code**：成功 0、失敗非 0，方便 Makefile / CI 整合。

推廣版 `encode_c` 可以改成支援行號：

```python
def encode_c_at(line, lineno, src_path):
    try:
        return encode_c(line)
    except (KeyError, ValueError) as e:
        raise CompileError(f'{src_path}:{lineno}: {e}')
```

### 7.2 兩遍合併成一遍（Single Pass + Patch）

記憶體與速度的雙重考量下，可以只用一趟：先假設「沒見過的符號都是變數」，最後若在 `.hack` 尾端發現前方衝突，再補一遍修正。典型做法是「**先產出、後 patch**」：把 `@LOOP` 暫時填 `0`，記下位置，等 `(LOOP)` 出現時再回填正確位址。這樣符號表不必等待標號，代價是要能「回頭改已輸出的位元」。

```python
# 概念示意：先佔位
pending = {}     # 未確定符號 → 已輸出的行號清單
...
if symbol not in st:
    pending.setdefault(symbol, []).append(len(codes))  # 記下位置
    codes.append('0' + '0' * 15)                       # 先填 0
...
# 等到 (LOOP) 出現時回填
def fixup(symbol, address):
    for idx in pending.get(symbol, []):
        codes[idx] = '0' + format(address, '015b')
```

### 7.3 支援其他平台：從「組譯器」到「交叉組譯器」

Hack 只有 A/C 兩種指令，所以組譯器超簡單。真實的目標平台各有各的編碼格式：x86 可變長度、RISC-V 六種格式、ARM 條件碼……組譯器的骨架（清理→解析→查表→拼碼）**完全不變**，變的只有「編碼表」與「指令格式」——這正是本書 1.1 節 RISC-V 章節會看到的通用結構。因此，你手上這個 Hack 組譯器，等於已經學會了所有組譯器的共同骨架；換目標平台，只是換一張表的事。

### 7.4 進一步的優化方向

- **程式碼膨脹（size）**：兩個版本對比 `.hack` 行數，驗證「優化真的變小」；
- **速度（speed）**：善用 Python 的 `dict` 已是雜湊表；更大的程式可換 C/Rust 或做「行號表預先計算」；
- **可讀性**：支援 `include` 檔（把常用常式抽出去）、條件組譯（`#ifdef`）、算術運算式（`@73+2`），一步步走向真正的編譯工具鏈。

## 8. 本章小結

- 組譯器測試分五關：**準備 → 編譯 → 格式檢驗 → 模擬器執行 → 比對已知答案**。
- 測試要拿「結果可心算」的程式當樣本：`1+...+5 = 15`、`1+...+100 = 5050`，答案由人類數學擔保，組譯器與程式都逃不掉。
- CPU 模擬器是最終裁判：載入 .hack、觀察 RAM，終值與預期不符就一定有 bug。
- 完整對照表（.asm ↔ .hack ↔ 譯碼解讀）是除錯組譯器的利器，同時也訓練你把編碼規則變成反射。
- 常見錯誤可歸為六大類：行號錯位、符號混淆、大小寫/錯字、註解殘留、常數越界、拆解順序——各有對應的快查法。
- 組譯器可以往「錯誤回報、單遍掃描＋回填、多平台表驅動、條件組譯」等方向延伸，骨幹不變、換表即可。

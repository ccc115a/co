# v0.7 — ch12 OS 在 hackemu 上執行

> 狀態：🚧 進行中（2026-09-10）
> 目標里程碑：**M7 — 把 `12/*.jack` 整包 OS 編譯、開機、執行，並在 hackemu 的
> GUI 上跑起需要 OS 的應用程式（例：Pong），可實際玩。**

## 一句話

把 v0.5 的工具鏈（`jack2vm` → `vm2asm` → `hackasm` → `hackemu`）接到課程
第 12 章：先編譯「OS + 應用程式」的 Jack 原始碼，經多檔 bootstrap
（`SP=256` + `call Sys.init 0`）開機，最後在 hackemu GUI / headless 執行。
若成功，`_eda` 這套工具就能跑完 Nand2Tetris 全專案。

## 執行鏈路（本版實作）

```
gen/os_src/（裁剪版 OS 8 檔） ──jack2vm──▶ *.vm     11/jack/Pong/ ──jack2vm──▶ *.vm
      └──────────────────────────────┬──────────────────────────────┘
                      vm2asm（多檔，bootstrap call Sys.init 0，label 依函式 scope）
                                       │
                                       ▼
                                     gen/*.asm ──hackasm --bin──▶ gen/*.bin ──hackemu──▶ GUI / headless
```

### 32K ROM 的硬限制（本版最重要的發現）

Hack 的 `@x`（A-instruction）**只有 15 個位址位元**，MSB 是 A/C 判別元：
`@x` 對 x>32767 根本沒有編碼。因此 **ROM > 32768 words 的程式，結構上
無法在 Hack 上執行**——不是模擬器的問題，任何仿製 CPU 皆然。

- 全 OS（8 檔）+ 最小 app 組譯出來 = **35330 words > 32K**，失敗。
  元兇是 `Output.jack` 的 16 進字型 push 資料（~16.8K 組語字）。
- vm2asm 密度 ≈ 35330 / 3422 行 VM ≈ **10.3 文本 word/VM 行**（良好目標 5–6）。
- Nand2Tetris 官方論壇共識：OS 塞 32K 「能做得到、但不強求」
  （在 VM Emulator 跑也是正解）。
- **本版方案 = 裁剪版 OS**：
  - 官方站台：`Array / Keyboard / Math / Memory / Screen / String`（不改）。
  - 自訂 `Sys.jack`：`Memory.init → Math.init → Screen.init → Keyboard.init
    → Main.main`。**Memory.init 必須最先**：`Math.init` 會 `Array.new(16)` 走
    `Memory.alloc`，freeList 未初始化（=0）時 alloc 會腐化記憶體
    （官方 Sys 是 Math 最先、Memory 最後，且官方 Memory.alloc 無 freeList=0
    防呆——官方順序在真工具鏈一樣會壞）。
  - 極簡 `Output.jack` 替身（gen/，非官方）：`moveCursor/printChar/printString/
    printInt/println/init` 全空實作，滿足 Pong 的「記分」呼叫、省 16.8K 字型。
    缺點：文字畫面不出字——這是取捨，完整字型版本以 M7.1 的 8/8 byte 證明為準。
  - 結果：`show.bin` 17770、`pong.bin` 29544，皆 ≤ 32768 ✓。

## 本版與「官方版」的程式碼修正差異

官方 nand2tetris `Screen.jack` 有兩個**知名 bug**（course tools 用 builtin OS
所以不會爆，但在「編譯真 .jack」的鏈路上必爆）：

1. `drawPixel`：`let mask = Math.two_to_the(x & 15));` 多一個 `)` → 嚴格
   compiler（我們的 jack2vm 與 C oracle 皆是）直接編譯失敗。
2. `clearScreen`：`while(i<8192){ let screen[i]=white; }` 忘了 `let i=i+1;`
   → **無窮迴圈**，Pong 一開場就卡死。

本版兩處皆已修（`nand2tetris/12/Screen.jack`）。`Screen.jack.md` companion
已同步。這是示範「官方 OS 也有 bug、修正要動手評估」的絕佳教材。

## 「兩塊球」的真相 —— `drawPixel` 位元方向 bug（v0.7.2 修正）

M7.3 的 ScreenTest 用「位元值」當標記，意外曝出 Pong 殘影的真兇：

- **兩塊球不是快照語意，是 `Screen.drawPixel` 的位元方向 bug。**
  HACK 把 word 的 **bit15（MSB）映到最左欄**；官方 `drawPixel` 卻用
  `mask = Math.two_to_the(x & 15)`，等於「bit 從 LSB 數」→ 每 16 欄以內
  左右反轉。全滿 word（bat 中間、地板線、長水平線）不受影響，所以
  M7.4 快照看不出來；但 6px 球的**邊緣碎段**一翻，就變成隔幾欄的兩塊。
  修正：`mask = Math.two_to_the(15 - (x & 15))`（`12/Screen.jack` 與
  `gen/os_src/Screen.jack` 同步，v0.7.2 起生效）。
- **「三段板」半擦殘影仍屬快照語意**：快照落在「白擦舊 bat → 重畫新 bat」
  之間所見的執行中狀態，不是撕裂（HACK 無光柵、無翻頁，雙緩衝無效）。
  遊戲幀約 3–4M instr、擦舊畫新縫隙僅數百 instr → 步數放大（預設 1M、
  滑桿上限 10M）即可把殘影機率壓到千分之一；按 **Pause** 通常落在完整幀。
- 為何之前「畫面慢」：GUI 只在事件時重繪（已修：每幀 `request_repaint()`）
  ＋ debug 版只有 ~32M instr/s；`--release`（~220M instr/s）後即順暢。

## M7.3 的兩顆雷（v0.7.2）

1. **`Screen.drawPixel` 位元方向**（同上節）——官方教材 OS 的 bit 序與
   HACK 不符，已在 `12/Screen.jack` + `gen/os_src/Screen.jack` 修正，
   `Screen.jack.md` 同步說明。驗證：`drawPixel(0,200)` 由
   `RAM[22784]=1`（bit0）改為 `32768`（bit15）。
2. **`jack2vm` 對混合算術「由左而右、無優先權」**：`16384 + 200*32`
   被編成 `(16384+200)*32`。此前沒中獎是因為 OS 內部多寫高優先權項在前
   （如 `(y*32)+(x/16)`）。測試端一律用顯式括號 `16384 + (200*32)`；
   compiler 本體（py/c 兩版）的修正留待下一版。
3. **標記槽不能用 RAM[300..] 區段**：SP=256 起往上長，800+ 的 call frame
   （Math.sqrt 等）會覆寫 300+ —— 標記統一放 RAM[100..=110]（stack 之下、
   static ~16–34 之上，安全）。

## 待解問題 / 設計決策

1. ✅ **螢幕方向**：實測 ball/drawPixel 落點與位址公式
   `16384 + y×32 + x/16`（bit15 向右）一致，方向問題解除（v0.6 掃尾誤警報）。
2. ✅ **`Sys.wait` 忙迴圈**：`wait(50)` 約 1 萬條指令；Pong 每幀多次 →
   模擬很慢。**維持真硬體語意**（不特判），用 `--release` 版 + Speed 上限即可順玩。
3. ✅ **KBD 語意**：與 OS 預期相符；`Keyboard.readChar` 的按下→放開循環
   不需改核心。
4. ✅ **多檔 byte 相容**：M7.1 已 8/8。又修了 vm2asm 多檔 mode 的
   function label scope（`WHILE_EXP`/`END_` 撞名）——單檔 mode 維持與 C
   逐位元相同（課程節語料有 raw label）。C 不比對的只有 bootstrap + scope。
5. ⏳ **`Memory.loadBin`（選做）**：讓 hdl2rs 的 Computer 也能直接 load `.bin`。

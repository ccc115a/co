## 本版實作內容

### 時序模型：回饋迴圈的雙輪 cascade（hdl2rs/gen.rs）

Computer 的 parts-eval 順序是 `[CPU, Memory, ROM]`，而 `eval()` 期間 memory 的
`w_inM`/`w_loadM` 取值來自 **CPU 的 `outM`/`writeM`**、CPU 的寫回又靠 ROM 的
instruction……同一個時鐘內，`w_*` 是**互相依賴的組合電路環**，任何固定順序都會
一步取到 garbage。

修法（`sample()` 內）：取樣有狀態 children 之前，用**同一組 `w_*` wire 變數**
（**不重新宣告**，重新宣告會 `let mut` 遮蔽成 0）**再跑一輪完整的 parts-eval**。
`eval()` 是純函式（只有 `sample()` 才真正改狀態），所以第二輪無副作用，只是把
環路收斂到一致值再交給 children 取樣。此雙輪只在**有回饋**時產生——`has_feedback()`
判定「存在同時有 sequential writer 與 sequential reader 的 wire」，只有 Computer
（與它之下）觸發；Bit/Register/RAM/PC 等一律**單輪**，行為不變。

`emit_cascade` 因此拆成 `emit_wire_decls`（宣告）+ `emit_parts_eval`（賦值），
第二輪只呼叫後者。

### 解析器修復（hackrt/tst.rs）

1. **`" load "` 誤判**：`parse_step_text` 用 `cmd.find(" load ")` 判斷 ROM-load 步驟，
   而 `set load 1` 也含 `" load "` → 被當成 `set load ROM32K-file`（chip=`set`、
   file=`1`）而**靜默丟棄**。後果：全部 ch03 循序晶片（Bit/PC/Register/RAM8/…）在
   `set load` 後寫空值 → verify 大回歸。修正：只有當「該 token 是 cmd 第一個空白
   token」且不在關鍵字清單　　　`["set","echo","repeat","while","eval","tick","tock",
   "output","clear-echo","compare-to","output-file","output-list","load"]` 內才算
   ROM-load。
2. **echo 的逗號**：`parse_seq` 又用 `trimmed.split(',')` 把 `echo "… select the
   'Screen' option, …"` 中的逗號再切開，造成「無法辨識的指令：select the」。
   lex_raw 已解出頂層分隔，多餘的 split 拿掉。

### ch04 驗證（hackasm、mult/fill harness）

- hackasm `encode_c` 把 `rest[..i]` / `rest[i+1..]` `.trim()`，支援 `D; JLE`、
  `0; JMP`（分號後空白）。組譯：`04/mult/Mult.hack`（16 行）、
  `04/fill/Fill.hack`（38 行），與官方行數一致。
- 官方 `Mult.tst`/`Fill.tst` 是 CPU Emulator 語法（`ticktock`、`set PC 0`、
  `RAM[0]`），不適用，故自寫跑在 Computer.hdl 上的 harness：
  - `04/mult/Mult-hw.tst`：reset pin + `ROM32K load` + sentinel `RAM16K[2] -1`，
    六節 `repeat {tick, tock}` 對應官方檢查點；結果 **0,0,0,3,8,42** 與官方一致。
  - `04/fill/Fill-hw.tst`：`set Keyboard 0`（全白）→ 跑 2000 ticktock →
    `set Keyboard 7`（全黑）→ 再跑 2000。只驗證**一部份幀**的穩定區段
    （SCREEN[94] 必白、[118]/[189] 必黑，見檔內註解），避免 8192 格 × 全閘層的
    漫長模擬。

### Screen/Keyboard 別名（hdl2rs/gen.rs）

`probe_whole/probe_indexed/set_whole/set_probe` 的 part 比對改用
`part_name_cond()`：`Screen` 附 `SCREEN`、`Keyboard` 附 `KBD` 別名，因為
Memory.hdl 的 part label 是 `Screen`/`Keyboard`，而課程慣例寫 `SCREEN`/`KBD`。

### `--release`（hdl2rs/main.rs）

debug 全閘層模擬極慢（Computer 六測試 ~2.5 分、Mult-hw 630 ticktock 6 分鐘）。
新增 `--release`：建置產出的 sim crate 時走 release profile、改跑
`target/release/{top}_sim`。Mult-hw 由 ~6 分鐘降到 ~15 秒（含編譯）。

## 本版遇到的坑（處理過程）

1. **ComputerAdd「寫不進去」**：debug 直覺是 Write 有問題，其實是**回饋環路**
   在單輪 cascade 下取到 garbage `writeM`/`inM`，Register/RAM 照單全收。
   先用 minimize 的 `--keep` 產物（`gen/Computer_sim/`）逐層 probe 定位到
   Memory 的 `w_loadM` 來    自 CPU 未收斂的輸出，才確認要「雙輪」而非「改順序」。
2. **第二輪遮蔽**：第一次做出雙輪是整段 `emit_cascade`（含 `let mut w_*`）重跑，
   wire 被遮蔽回 0 → 全錯。固定成「只重跑 `emit_parts_eval`，不重宣告」。
3. **`" load "` 大回歸**：解掉 Computer 後 verify 反而爆一批 ch03，才挖出
   `set load` 被當 ROM-load 的解析器 bug；這解釋了為何「最近每次改動都炸循序
   晶片」。
4. **echo 逗號**：ComputerRect.tst 裝不下、報「無法辨識的指令：select the」，
   是 `parse_seq` 二次 split 把引號內的逗號切開，非 echo 支援問題。
5. **`SCREEN[94]` 挖洞**（`*`）：probe 用 part label `Screen` 對不上慣用名
   `SCREEN`，回傳 `None` → 整欄 `*`。加別名後正常。（表頭 `SCREEN[94`` 少 `]`
   是官方「表頭截斷到欄寬」行為，非 bug。）
6. **效能**：debug 跑 630 ticktock 的 Mult 要 6 分鐘、Rectangle ~1.4s/tick，
   `--release` 後 Mult/Fill 各 ~15 秒含編譯；Fill 只驗部分幀避開 8192 格全量。

## 已知限制 / 待辦（next）

- `keyboard_cond`/`continue`（互動式 `.tst`）未實作，`Memory.tst` 無法納入自動化。
- `RAM[addr]` 於 tst 層的索引寫入（`set RAM[0] 3`，無 address pin）仍走
  `set_whole RAM16K…` 慣用別名（`RAM16K[0]`），語意約定與 `SCREEN[]`/`KBD` 一致。
- Mult/Fill 只驗「行為等價」，未跑官方 `.tst`（CPU Emulator 語法）；ch06 組譯器
  完成後可端到端比較。
- 全閘層模擬仍偏慢；未來可考慮 cache 子樹或改用 bit-parallel 求值。

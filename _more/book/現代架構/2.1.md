## 1. Cache 存在的理由：Memory Wall

CPU 與記憶體之間的效能差距是計算機架構最根本的鴻溝：

| 層級 | 典型容量 | 典型延遲 | 成本/bit |
|------|----------|----------|----------|
| Register File | ~數百 B | 1 cycle (~0.3 ns) | 最高 |
| L1 Cache | 32–64 KB | 2–4 cycles | 高 |
| L2 Cache | 256 KB–1 MB | 10–20 cycles | 中 |
| L3 Cache | 2–32 MB | 30–80 cycles | 低 |
| DRAM 主記憶體 | 8–64 GB | 80–200 cycles | 很低 |
| SSD | 數百 GB–TB | 數萬 cycles | 最低 |

如果每條 load 都去 DRAM 拿資料，CPU 會被卡在 **Memory Wall** 上。Cache 利用程式的**時間區域性（Temporal Locality）**與**空間區域性（Spatial Locality）**——同一資料短時間內重複存取、相鄰資料連續存取——把大部分 load/store 命中在 ns 級的快取內。

### 1.1 平均存取時間 (Average Access Time)

$$
\text{AMAT} = T_{\text{hit}} + \text{MisRate} \times T_{\text{miss}}
$$

- $T_{hit}$：命中時的存取延遲（如 L1 = 4 cycles）。
- $MisRate$：不命中比例（如 5%）。
- $T_{miss}$：往下層要資料的代價（如 L2 = 200 cycles）。

例：L1 hit = 4 cycles、miss = 200 cycles、misrate = 5% → AMAT = 4 + 0.05×200 = **14 cycles**。可見 miss 成本極高；把 misrate 從 5% 降到 1% 就把 AMAT 砍到 6。

## 2. 直接對映、組相聯與全相聯

### 2.1 Cache 的位址切割

以 32-bit 位址、4KB Cache、每行 32 bytes（8 words）為例：

```
31                            12  11          6   5         2  1  0
┌────────────────────────────────┐ ┌──── Index ──┐ ┌ Block ─┐ ┌─┐
│              Tag               │ │  6 bits     │ │ 5 bits │ │ │
│      (位址的主體)              │ │  (Set #)    │ │  (byte offs)│
└────────────────────────────────┘ └─────────────┘ └────────┘─┘
```

- **Offset**：Block 內的第幾個 byte（block size 決定）。低位不需儲存，只做多工器選取。
- **Index**：指向某一 **Set**（或 Direct 的某一 Line）。
- **Tag**：真正比對是否命中的位址主體。

Block 數 = 總容量 ÷ Block Size。位址切割的 log2 計算：

- Offset bits = log₂(Block Size in bytes)
- Index bits = log₂(Number of Sets)
- Tag bits = 32 − Offset − Index

### 2.2 Direct-Mapped Cache（直接對映）

每個記憶體位址**只能**進唯一的 Cache Line：

$$
\text{Line} = \text{BlockAddress} \bmod \text{總 Lines}
= \text{(位址 ÷ BlockSize)} \bmod \text{Line Count}
$$

| 優點 | 缺點 |
|------|------|
| 硬體最簡單：只需 1 個 Tag 比較器 | 多個熱門位址若同 index 會**互相踢出（Ping-Pong）** |
| 存取延遲最低（無需多路選擇） | 產生大量 Conflict Miss |
| 功耗較低 | 巨大 miss 懲罰讓效能劇烈起伏 |

範例：8 個 Lines 時，位址 A、A+4KB、A+8KB 全都會落入同一 Line——若迴圈反覆存取 A 與 A+4KB，就會每回合互踢。

### 2.3 N-Way Set-Associative Cache（組相聯）

平衡設計：Cache 分成多個 **Set**，每個 Set 內有 **N 個 Way**（可放 N 塊）：

$$
\text{Set} = \text{BlockAddress} \bmod \text{Sets總數};\quad
\text{命中時需比對 Set 內 N 個 Tag}
$$

- **比例關係**：Sets數 × Ways = 總 Lines。直接對映 = 1-way SA；全相聯 = 「1 Set × 全部 Lines」。
- 容量不變下提高 N → 衝突減少，但比對路徑拉長（多路 Tag 同時比較 + 多工選擇），Hit Time 略增。
- 現代 L1（4–8 way）、L2/L3（8–16 way）取平衡。

### 2.4 Fully-Associative Cache（全相聯）

只有一個 Set，塊可放任意 Line。比對「所有」Tag → 使用 **CAM（Content-Addressable Memory）**逐位元平行比較，每次全部線路都翻動：

| 優點 | 缺點 |
|------|------|
| 零 Conflict Miss（只有 Cap./Comp. Miss） | 每個 cycle 全部 Tag 平行搜尋 → 功耗 & 面積爆炸 |
| 軟體刪除對齊限制 | 只適合**小容量**（如 TLB，通常 64–512 entries） |

這就是為何 TLB 用全相聯而 L1 用組相聯——全相聯的功耗與容量成比例，只在小表上划得來。

### 2.5 設計空間總表

| 特性 | Direct | N-way SA | Full Assoc |
|------|--------|----------|-----------|
| 比對器數量 | 1 | N | Lines 數 |
| Hit Time | 最快 | 略慢 | 慢（大型） |
| Power | 最低 | 中 | 高 |
| Conflict Miss | 嚴重 | 中 | 無 |
| 典型用途 | 早年 | 主流 L1/L2/L3 | TLB |

## 3. 寫入策略 (Write Policy) 與替換演算法

### 3.1 Write-Through vs. Write-Back

| | Write-Through | Write-Back |
|---|---|---|
| 寫入動作 | 同時更新 Cache **與** 下一層 | 只更新 Cache，Line 標上 **Dirty** |
| Dirty bit | 不需要 | 需要 |
| 寫回時機 | 每筆寫都要 | 該 Line 被替換（Evict）時才寫回 |
| 匯流排頻寬 | 高（寫放大） | 低（現代主流） |
| 一致性命題 | 下層永遠最新的資料 | 下層可能過時，需載入方共享協議（3.1 節） |

- Write-Through 常搭配 **Write Buffer**（小型 FIFO），寫入先入 buffer 再落盤，CPU 不等待——但仍舊頻寬換簡單。
- Write-Back 是現代 CPU 的主要機制，特別在 L1/L2。

### 3.2 Write Allocation Policy

Write Miss 時要否將該 Block 移入 Cache？

| 策略 | 動作 | 適用 |
|------|------|------|
| **Write-Allocate**（取回） | 先把 Block 載入 Cache 再寫 | 常配 Write-Back（寫後很快就會再讀） |
| **No-Write-Allocate**（寫直通） | 不載入，直接寫下一層 | 常配 Write-Through（整格寫入的流） |

現代 CPU 常見搭配：L1/L2 **Write-Back + Write-Allocate**，store miss 時把整行取回再標 dirty。

### 3.3 替換演算法 (Replacement)

當 Set 滿了必須逐出一個 Way：

| 演算法 | 機制 | 優點 | 缺點 |
|--------|------|------|------|
| **LRU**（Least Recently Used） | 記錄 Line 的使用次序，剔除最久沒用的 | 最接近最佳 | N-way 高（N=8+）時更新邏輯與面積貴 |
| **Pseudo-LRU (PLRU)** | 用樹狀位元寫入/抬升近似 LRU | 硬體輕量（只需 N-1 bits） | 非精確，但實際表現極接近 LRU |
| **FIFO** | 依進 Set 順序踢 | 最簡單 | 會把「剛載入卻要立刻被用到」的熱行踢掉 |
| **Random** | 隨機踢 | 零面積、零狀態 | 誤殺率高、可能反覆踢同一熱行 |

**Belady 異常**：FIFO/Random 下，加大容量反而可能使 miss 增加（不滿足 stack property）。LRU 等「stack 性質」策略則保證容量越大越好。

## 4. 快取不命中 (Cache Miss) 分類：3C 分析

三類 miss（Ahmed-Hill 3C）診斷「被浪費的容量到哪去了」：

### 4.1 Compulsory Misses（強制/冷啟動不命中)

資料**第一次**被存取必定 miss——Cache 永遠空著、無關容量。

- 特徵：容量增大也無法消除；程式冷啟動與 context switch 後最明顯。
- 解法：
  - **增大 Block Size**：第一次存取抓整行，後續相鄰資料變「免費」hit。
  - **硬體 Prefetcher**：如 Sequential Prefetcher——偵測到「PC 連續 +4 的存取模式」就提前抓下一行（現代 L2/L3 標配）。

### 4.2 Capacity Misses（容量不命中）

程式工作集（Working Set）大於 Cache 容量時，被擠出的行必須重新載入。

- 特徵：加大 Cache 可直接消除，純粹「空間不夠」。
- 解法：加大 Cache、更好的資料結構（分區）、更好的替換策略。

### 4.3 Conflict Misses（碰撞不命中）

「Set 夠多」但「同一個 Set 太忙」：多個熱門位址映射到同一 Set，雖總容量充足仍互相踢出。

- 特徵：提升 Associativity（如 4→8-way）能減輕；調整資料結構對齊能避開嗑同 Set。
- 解法：
  - 提高 associativity；
  - **Padding / 對齊**：讓熱門陣列分散於不同 Set（如 `alignas(64)` 錯開）；
  - **Victim Cache**（小型全相聯旁路）承接被逐出的行，給它們第二次存活機會。

### 4.4 3C 診斷範例

| 場景 | 主要 miss 型別 | 改善手段 |
|------|---------------|----------|
| 逐元素連續掃過大陣列 | Compulsory + Capacity | 較大 Block + Hardware Prefetcher |
| 兩個大陣列互相層疊存取同一 Set | Conflict | Reduce aliasing / Padding |
| 迴圈反覆存取超過容量的資料集 | Capacity | 加大 Cache |
| 新 process 剛啟動 | Compulsory | 一併載入（如計量 warmup） |

## 5. 現代 Cache 進階取捨

### 5.1 階層式設計

```
CPU core
   │  （虛擬位址）
   ▼
L1-I (VIPT)     L1-D (VIPT)       ← 5–10 cycles，低延遲但小
   │                │
   ▼                ▼
L2 (unified, PIPT)              ← 10–30 cycles
   │
   ▼
L3 (unified, shared across cores) ← 30–80 cycles，跨核心共享（見 3.1 Coherence）
   │
   ▼
DRAM
```

L1 分 I/D 的原因：IF 與 MEM 的存取在管線中是偏移的，分開可避免互相搶 — 這也解決 `IF` 與 `MEM` 兩個階段的結構性冒險。

### 5.2 Multi-ported / 銀行化 (Banked)

L1-D 需要同時服務多個 load（OoO 核心 2-3 個），常切成多個 Bank（如 4 banks）平行存取不同 banks；同 bank 衝突才需序列化。

### 5.3 Prefetching 的警戒線

Prefetcher 是 Compulsory miss 的利器，但**過度 prefetch** 會污染 Cache：佔用容量、踢出熱行、浪費頻寬。現代設計（如 L2 next-line + stride prefetch，外加 ML-based）偵測存取模式才動作。

### 5.4 其它小工具

- **Victim Cache**：承接被逐出的行（小、全相聯），把 conflict miss 的二次機會成本壓低。
- **Streaming Buffer**：針對順序流的微 prefetch。
- **Knights Landing / 加速器式 MC**：例如統一大容量 L2 的成本權衡。

## 6. 動手算：一個完整設計範例

**設計題目**：64KB、4-way Set-Associative、每行 32 bytes、32-bit 位址。

1. Block Size 32B → **Offset = log₂32 = 5 bits**。
2. 每 Set 幻線數 = 64KB ÷ 32B ÷ 4-ways = 512 lines/set → **Index = log₂(512) = 9 bits**。
3. **Tag = 32 − 5 − 9 = 18 bits**。
4. 總 entries = 64KB / 32B = 2048 lines；Tag 儲存總量 = 2048 × 18 bits ≈ 4.6KB（佔容量約 7%）。

命中流程（SA）：

1. 取 Index → 定位 Set。
2. **平行**比較 4 個 Tag（4 個比較器）。
3. 命中 → 用 Offset 挑出 word；反之 miss → 依替換策略 evict 一個 Way 後取回。

## 7. 小結

- Cache 靠區域性賭博：用簡單硬體換取大多 hit、少數 miss。
- Direct（最簡）、SA（主流最平衡）、Full（無衝突但只適合小表如 TLB）。
- Write-Back + Write-Allocate 是現代主流；替換用 PLRU/LRU 守住工作集。
- 3C（Compulsory/Capacity/Conflict）模型幫你對症下藥。

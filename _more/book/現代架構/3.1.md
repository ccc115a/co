## 1. 快取一致性問題

### 1.1 多核心的私有快取

現代多核心 CPU 每個核心有自己的 **L1/L2 私有快取**，共享一片 L3（和 DRAM）。當多個核心同時快取同一份記憶體時，寫入動作就會造成不一致：

```
Core 0            Core 1
 │ L1: A=5        │ L1: A=5（從主記憶體複製）
 │                │
 │ 寫 A=7        │（沒人通知它）
 │ L1: A=7 (dirty)│ L1: A=5（過期！）
```

若 Core 1 現在讀 A，它看到的是舊值 5——破壞了程式對記憶體的基本直覺。

### 1.2 一致性（Coherence）的里程碑定義

來自 Hennessy & Patterson 的經典定義，一份記憶體視為一致的系統需滿足：

1. **Write Propagation（寫入傳播）**：任一行上的寫入最終會被所有其他處理器看見。
2. **Write Serialization（寫入序列化）**：所有處理器看到對**同一位置**的寫入順序必須相同（即每個 write 都有全域總次序）。

核心（也常見表述）；同時它的動作以「Single-Writer / Multiple-Reader」隱含：任何時刻，一個 Cache Line 只允許**一個節點持有寫權（exclusive）**，或**多個節點僅持有讀權（shared）**。

### 1.3 Coherence vs. Consistency（預告）

- **Coherence**：針對「單一記憶體位址」在眾核心之間的讀寫次序。
- **Consistency（3.2）**：針對「多個不同記憶體位址」的讀寫在全域的次序模型。
兩者關聯：Coherence 提供「每位置的總序」，Consistency 定義跨位置的「程式次序如何被重視」。先把 Coherence 談完。

## 2. Snooping（監聽式）一致性協定

### 2.1 機制

所有核心的快取控制器**共同連在一條共享匯流排（/同一個 coherence 點）上**。任何核心要進行記憶體操作（讀/寫/逐出），都會把動作廣播到匯流排，其他核心的 Snooper 監聽並據以更新自己的狀態：

```
       BusRead(addr A=7)
         │
   Core0 ──► 廣播到 Bus ─► [Snooper Core1]
         │                    │ Core1 若也持有 A 的副本
         │                    │ → 提供資料 / 失效自己的 copy
         ▼
    主記憶體 / L3
```

常見匯流排事件：

| 事件 | 意義 |
|------|------|
| `BusRd` | 某核心要讀（若它沒有有效副本） |
| `BusRdX` | 某核心要獨佔寫（全體必須命自己失效） |
| `BusUpgr` | 核心已持有共享副本，要求升級為獨佔寫 |
| Flush / WriteBack | Dirty 資料回寫主記憶體 / 轉交給他人 |

### 2.2 優點與限制

- **優點**：簡單、局部硬體、隱含的寫序列化（匯流排是全域次序點）。
- **限制**：每次獨佔寫都要廣播 → 對**小型系統（通常 ≤ 8 cores）**成立；核心數增加後廣播流量以 $\mathcal{O}(N^2)$ 成長，一律成為瓶頸。

### 2.3 寫序列化靠什麼保證？

Snooping 系統本質上依賴**「某個點對每一筆存入都有全序」**——共享匯流排仲裁（2.3 節）確保同時只有一個 BusRdX 通過，寫入次序＝通過匯流排的次序。分散式請款（無法共享總線）時才需要目錄式。

## 3. Directory-Based（目錄式）一致性協定

### 3.1 動機

Snooping 的廣播流量 $O(N^2)$ 讓大規模（64+ cores, NUMA）不可行。目錄式協定用**「每個 Cache Line 的持有者清單」**取代全域廣播：

- 在主記憶體（或共享 L3）旁設立 **Directory**：
  - 每個 Cache Line 一筆 entry：誰持有（**Sharer Vector**）、狀態（Uncached / Shared / Modified…）。
- 需要寫獨佔時：查目錄 → **精準 Unicast/Multicast**（只通知有分享的核心）發送 **Invalidate Message**，不需廣播。

```
 Core0 寫 A ─► 目錄查：A 被 {Core1, Core3} 共享
                └─► 只向 Core1 & Core3 發 Invalidate
                （其它核心零干擾）
```

### 3.2 通訊成本分析

- 目錄協定：每筆寫獨佔的操作通訊 O(#sharers)，通常 ≪ N。**NUMA（Non-Uniform Memory Access）**系統（每個節點自己的 DRAM + Directory）才能把各自片段的存取保持「本地」。

### 3.3 代價

- Directory 本身佔記憶體：「每 line 一筆 bit vector」——Sharer Vector 長度 = 核數。給大型機（1K cores）吃 1K bits/line 就會爆成本 → 靜態/dynamic sharing tracker、有限目錄（只記有限 sharers，超過需降級廣播）。

## 4. MESI 協定（具 Snooping 導向的狀態機）

### 4.1 四種 Cache Line 狀態

| 狀態 | 全名 | 副本數 | 與主記憶體一致性 | 代表含義 |
|------|------|--------|------------------|----------|
| **M** | Modified | 唯一 | **不一致（Dirty）** | 已被此核心修改，主記憶體過期 |
| **E** | Exclusive | 唯一 | 一致（Clean） | 此核心獨享，未修改 |
| **S** | Shared | 多份可能 | 一致（Clean） | 多核共享，無需通知他人即可讀 |
| **I** | Invalid | 0 | — | 無效，存取會 miss |

M 是最「值錢」的：資料最新、獨家、可安心覆寫不需寫回。

### 4.2 狀態轉移（以「讀」「寫」觀察）

以 Core 為中心的典型轉移：

```
                  BusRdX (別人要寫)              Write hit (本地寫入)
   I ───────────► E ──────────────────────► M
   │                     │                    │
   │ BusRd (別人讀)      │                    │
   ▼                     ▼                    ▼
   S ◄───────────────────┘  ← 改為共享      （讀 hit 於 S/M/E 皆可）
   │        Write hit（本地）
   └──────────────────────► M（改為 dirty，需先 Invalidate 其他 sharers）
```

關鍵動作：
- **Read**：I → (miss) BusRd → 若無他人持有則 E、否則 S。
- **Write hit 於 S**：需發 BusUpgr（無讀資料，純升級）讓其他人失效後轉 M。
- **Write hit 於 E/M**：不需任何匯流排動作（本地改）。
- **M 被其他核心讀**：該核心需把 dirty data 提供給它（不必寫回 DRAM；見 MOESI）。

### 4.3 寫 Serialization 的落地

MESI 每個狀態不可侵犯 Single-Writer：M/E 時全域只有一份；寫 S 前必先找滿所有 sharer 並等它們回 ACK（若無 ACK，硬體需保證其他 core 對「之後才程式可見的寫」維持一致）。「同一位置各 core 看到相同次序」由此達成。

## 5. MOESI 協定：加上 Owner

### 5.1 Owner (O) 狀態

MOESI 在 MESI 基礎上增加 **Owner**：

| 狀態 | 說明 |
|------|------|
| **M** | 唯一、dirty、主記憶體過期 |
| **O** | **dirty 但是共享**：多核持副本，但「資料只有一位 Owner 那顆是唯一的 dirty」 |
| **E/S/I** | 同 MESI |

### 5.2 O 狀態帶來的輸贏

- **O 的救援**：Owner 回應他人的讀請求，**不必先寫回主記憶體**。
  - 例：Core0 把 A 改成 dirty（M），Core1 要讀 A。MESI：Core0 需把 A 寫回 DRAM（或直接把資料送上 Bus + 記錄 dirty）才讓 Core1 讀到。
  - MOESI：Core0 直接送 A 給 Core1，Core0 轉 **O**、Core1 轉 **S**（資料主幹在 O，主記憶體仍悶著舊值）。
  - 結果：**DRAM 存取次數大減**（不用 flush）——共享大量處理器、多個核心同時讀同一 dirty line 時尤其划算。

### 5.3 狀態轉移的差別

```
   M ──(BusRd from other)──► O（繼續當資料源頭，不寫回）
   O ──(BusRd, 再一個 sharer)──► S 維持 (還是 O，資料沒變)
   三者（M/E/S）都能回應「讀的資料」：M/O 提供新資料，E/S 提供與記憶體一致的值。
```

## 6. 虛假共享 (False Sharing)：Coherence 的頭號效能殺手

### 6.1 成因

不同核心上的「**不同變數**」落在**同一個 Cache Line（如 64B）**內。即使它們邏輯上完全無關，硬體的一致性單位是「整條 Line」——一方寫入就會「無辜地」使另一方的 Line 失效：

```
Core0 頻繁寫 A[0]      Core1 頻繁寫 A[1]
記憶體: | A[0] | A[1] | ← 同一個 64B line！
         └─────────────┘
Core0 寫 → Snoop 看到 Core1 也持有此 line → 發 Invalidate
Core1 寫 → 觸發同樣的乒乓……
→ 兩個核心間每筆寫都互相摧毀 / 重新載入同一 line（Cache Line Bouncing）
```

程式明明沒有共享變數，效能卻血崩——因此叫「虛假分享」。

### 6.2 解決方案

1. **資料結構對齊 / Padding**：放大結構讓熱門欄位各佔獨立 Cache Line：

```c
struct alignas(64) CounterPerCore {
    int value;        // 每個核心自己的欄位
    char pad[60];     // 填滿到 64B 界線，避免與鄰居共享 line
};
```

2. **拆分欄位**：如多核心各寫自己的 `result[i]` 陣列，再合併。
3. 跨過核心的行為用 `[[likely]]` 時注意 line 邊界。

### 6.3 檢測

- perf 工具看 `cacheline_contended` / LLC miss 比率飆高；
- 資料同 line 的兩個 hot 變數是重點線索。

False Sharing 跟 Coherence Protocol 本身無關——它是程式對 Cache Line 組織的誤用，在 **MESI/MOESI 的保證下其實非常「正確」**（兩邊都得到自己的寫入），只是效能恰是災難。

---

## 7. 小結

- Coherence 解決「同一位置」的寫序列化 + 寫傳播。
- Snooping（≤8 core，重用匯流排）與 Directory（大型/NUMA，精準無效化）兩條路線。
- MESI 四狀態定義了單寫/多讀的彈性；MOESI 的 O 讓 dirty 資料不必寫回就可分享。
- False Sharing 是 line 粒度下的程式陷阱，靠對齊/Padding 破解。

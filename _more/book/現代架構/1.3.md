## 1. 為什麼要預測分支？

在 1.2 節結尾，我們看到 Branch 的確認延遲（EX 階段）造成每次被動 stall 或 flush 的損失：

- **無預測（stall 等待）**：每個 branch 損失 2 cycles。
- **靜態預測 Not-Taken + Flush**：每次誤判損失仍達 2 cycles。

Branch 佔典型程式指令的 **~15%–20%**。若無任何動態預測，管線治理效率會大打折扣。**動態分支預測器**在位元層級記住歷史，預測下次的跳轉行為，把有效損失壓低到平均 < 0.1 CPI。

**效能量化**：假設 branch 佔比 $f=0.2$，每次 mispredict 懲罰 $p=15$ cycles（深度亂序管線的取指已拉得很遠），平均預測失準率 $m$：

$$
\text{CPI}_{\text{avg}} = 1 + f \cdot m \cdot p
$$

當 $m=20\%$（弱預測器）→ $1+0.6 = 1.6$；
當 $m=5\%$（強預測器）→ $1+0.15 = 1.15$。在現代 7-15 stage 管線下，好的預測器幾乎是能不能用 ILP 賺效能的關鍵。

## 2. BTB 與 BHT：記住「在哪跳」與「怎麼跳」

動態預測的兩大記憶體結構（都位於 **IF 階段**，因為決策必須在取指當下做出）：

### 2.1 BTB (Branch Target Buffer)

**記錄「Branch PC → Target Address」的對映**（前方快取）。

- 因為 branch target 是 PC-relative（位址 = PC + offset），**要在 IF 階段就算出 target**，就得知道 offset——那是 decode 後才知道的。
- BTB 讓 IF 階段**看到 branch PC 就直接輸出 target**，不需等 decode。
- BTB 也被稱為「分支目標快取（Branch Target Cache）」或「下一位址快取（Next-Address Cache）」。

```
┌─ IF 階段 ───────────────────────────────┐
│  PC ──► 查 BTB                              │
│         ├─ Hit + 預測 Taken → TargetAdr 直接給 IF 取指 │
│         └─ Miss                 → 當作 sequential fetch │
└──────────────────────────────────────────────┘
```

#### BTB 抽象實體（通常為 Direct-Mapped / Set-Assoc 的小型 CAM 或 SRAM）：

```
| Valid | Tag = branch PC | Target = 目標絕對位址 | 狀態(可選：與 BHT 合併) |
```

用 **Branch PC 的低位**作為 index，Tag 作比對。Tag 與 Target 都存絕對 PC（相較 BHT 只存 T/NT 位元，BTB 的資料寬度更大）。

### 2.2 BHT (Branch History Table)

**記錄「歷史跳轉行為（Taken/Not-Taken）」**。

- 早期設計：每個 entry 一個 bit（1 = 上次 taken）。**問題**：單一 bit 無法抵抗「迴圈只有最後一次不被採取」的抖動（把迴圈結尾的 not-taken 誤當成常態）。因此現代 BHT 至少用 **2-bit**。
- BHT 也可以反向思考：以 PC hash 決定 BHT entry，是「**global**」還是「**per-PC（local）**」歷史，正是下一節的設計空間。

實際中，**BTB 與 BHT 常整合成單一「分支預測快取」**，一個 entry 同時含 target + 2-bit counter。下文分開介紹是為了凸顯功能差異。

## 3. 2-bit 飽和計數器 (2-bit Saturated Counter)

### 3.1 狀態機

以「Taken / Not-Taken」的 2-bit 編碼（如低位為方向位），4 個狀態：

```
                taken             taken             taken
  ┌─────────►(11) Strong T ──► (10) Weak T ──► (01) Weak NT ──► (00) Strong NT ◄────────┐
  │           ▲                 │                ▲                │                       │
  └───────────┘                 ▼ not-taken      ▼                │ not-taken              │
             not-taken        (10) ──────► (01)                    │                       │
                                                                    ▼ (00 persists)         │
  （實際上轉移：每遇一次 *與 D 相反* 才 -1；連續兩次相反的結果才會翻轉方向）
```

精確行為（2-bit 計數器，遇 taken 加 1，遇 not-taken 減 1，clamp 於 0..3）：

| 目前值 | 本次 taken | 本次 not-taken |
|--------|-----------|----------------|
| 00 (強 NT) | → 01 (弱 NT) | 00 （保持） |
| 01 (弱 NT) | → 10 (弱 T) | 00 |
| 10 (弱 T) | → 11 (強 T) | 01 |
| 11 (強 T) | → 11（保持） | 10 |

### 3.2 為何要 2-bit？

- **1-bit 的致命缺陷**：執行「重複 N 次的迴圈」時，迴圈尾的 `bne`（前 N-1 次 taken、第 N 次 not-taken）在 1-bit 預測器下「最後一次」與「退出後的第一次」一定會誤判。命中率約 $2/(N+1)$，對短迴圈可低至 ~50%。
- **2-bit** 要求「連續兩次」的方向改變才翻轉，因此：
  - 迴圈內部每一次的 taken 都命中 → 只有「loop exit」和「loop re-entry」兩次誤判，命中率 $\approx (N-1)/N$。
  - 加入 **hysteresis**（遲滯）效果，抗抖動。

### 3.3 索引方式：直接對應 PC

最簡單的 BHT 是 2-bit 計數器以 `PC[branch_index]` 直接索引（忽略低位——指令對齊），稱為 **per-PC 靜態索引**。問題：**不同 PC 的 branch 互相干擾（aliasing）**，且「同一個 branch 的週期性行為」無法被捕捉。

## 4. 2-Level 適應性預測器：捕捉分支關聯

### 4.1 動機：某些 branch 的行為取決於其他 branch

```
if (a) ... else ...     # B1
if (b) ... else ...     # B2
# 假設 a=b：B1 taken ⇔ B2 taken，兩個 branch 高度關聯
```

單一計數器看不到 B1、B2 之間的歷史。**2-Level 預測器**用「歷史」當成額外 index，與 PC 一起查表——這就是「**correlation (gshare)**」的力量來源。

### 4.2 結構：GHR + PHT

```
                    branch PC
                       │
  Global History       │（XOR）
  Register（GHR）:  ⚪ XOR ⚪
  例如 1 0 1 1 0        │
                       ▼
              ┌───────────────────────┐
              │  PHT (Pattern Hist.   │  ← 每個 entry 是 2-bit counter
              │   Table)              │
              └───────────────────────┘
                       │
                    預測值 T / NT
```

- **GHR（Global History Register）**：右移暫存器，記錄最近 N 個 branch 的**結果**（T=1, NT=0），如 `10110`。
- **PHT（Pattern History Table）**：2^N 個 entry，每個 entry 一個 2-bit 飽和計數器。
- **索引**：`Index = PC[N-1:0] ⊕ GHR` → 正是 **Gshare（global-history sharing）** 演算法。

### 4.3 Gshare 與 Gselect

- **Gshare**：`PC低N位 ⊕ GHR`。因為 XOR 混合了「哪條 branch」與「什麼歷史」，自然捕捉 branch 間的關聯。
- **Gselect**：直接 concatenate：`Index = {GHR, PC 高段}`（不混 Xor）。實作更簡單，但訊號互相干擾較重。
- **兩者比較**：Gshare 在多種 SPEC benchmark 上通常略優（少約 1-2% 失準率），實作成本幾乎相同——只差一個 XOR gate。

### 4.4 歷史長度 N 的取捨

- N 太短（如 2-4）：捕捉不了長迴圈模式。
- N 太長：PHT 需要 2^N 個 entry（記憶體爆炸），且同 PC 的長歷史稀疏、易 aliasing。
- 常見折衷：N = 6 ~ 24；硬體甘特圖上，現代處理器常見 **GBHR = 16~32 位 + 數百 KB 的 PHT**（已與 BTB 合併成「Branch Predictor + Branch Target Buffer」）。

### 4.5 擴充：Local History + 混合預測器

- **Per-Path / Local 歷史**：同一個 branch PC 自己的近期結果（Local History Register，LHR）當索引，捕捉「同一 branch 自身的週期性」（如每隔 3 次才跳一次）。
- **混合（Hybrid/tournament）預測器**：同時運行 global 與 local 兩個預測器，再用「選擇器（meta predictor）」於執行後投票選擇較準的一方，約可再省 1-3% 的失準率，代價是邏輯翻倍。Pentium 4 / Core 系列即此路線。
- **TAGE（TAgged GEometric）**：現代主流（Intel/AMD/ARM 高階核），用多個不同歷史長度的 tagged table + 最長歷史命中者勝出，Near-Perfect 但複雜度極高——在此僅作了解。

## 5. 其他重要機制

### 5.1 Return Address Stack (RAS)

函式 `call`/`ret` 的 target 並非規則（每個 call 點不同），BHT 幫不上忙。**RAS** 是獨立的小型堆疊（如 8-64 層），`jal`（call）時 push 返回位址，`jalr`（ret）時 pop 預測下一個 PC。準確率 90%+。

### 5.2 間接跳躍預測 (Indirect Branch)

如 `jr s0`、`jalr`（虛擬函式、switch-case jump table）。RAS 只處理 ret；其他間接跳躍得靠 **Indirect BTB**（ITBE，用 hash 記錄「PC → target」）。

### 5.3 預測失敗後的 Flush 深度

Branch 在 EX 階段才確認 → 追入管線下游的指令可能超過 N 條。現代亂序核心的 **misprediction penalty** 可達 15-20 cycles，因此並行使用「提早確認（Early resolve，如把 branch 比較放進 ID 階段）」「預測器快取（predictor 存在 I-Cache 旁）」「Fetch 寬度提高」等手法縮短它。

## 6. 從統計資料看預測器效果

| 預測器 | 失準率（典型 SPECint） | 實作成本 |
|--------|----------------------|----------|
| 靜態 Not-Taken | 30-50% | 0 |
| 1-bit BHT | 15-20% | 很小 |
| 2-bit per-PC BHT | 10-15% | 小 |
| Gshare (N=16) | 5-8% | 中 |
| Tournament/hybrid | 3-6% | 較大 |
| TAGE (高階) | <5% | 大 |

---

## 7. 小結

- BTB 告訴 IF 階段「下一個 PC」；BHT 告訴 IF 階段「要不要跳」。
- 2-bit 飽和計數器利用 hysteresis 抵抗迴圈結尾抖動，是 BHT 的基本單元。
- Gshare 用 `PC ⊕ GHR` 索引 PHT，把「誰家的 branch」與「最近的歷史」混在一起，捕捉 branch 間關聯。
- 高階處理器再用 RAS、Indirect BTB、hybrid/TAGE 補足邊角，把 mispredict 降到 1% 級別。

下一節（1.4，超純量與亂序執行）中，分支預測的功能被放大到取指寬度 4-8 條指令——沒有可靠的預測器，Superscalar 根本無法回填無資料的 fetch 視窗。

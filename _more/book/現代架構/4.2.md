## 1. 特權等級 (Privilege Levels) 與保護機制

### 1.1 RISC-V 的特權模式

| 模式 | ABI 名 | 使用者 | 權限 |
|------|--------|--------|------|
| U-Mode | User | 應用程式 | 最低：不能碰 CSR、不能碰受保護記憶體 |
| S-Mode | Supervisor | **OS Kernel** | 可用 `satp`/頁表、`stvec`/`scause`/`sepc`、可發 `sfence.vma` |
| M-Mode | Machine | Firmware / OpenSBI（bootloader） | 最高：可碰所有 CSR、PMP 管控 |

還有可選的 HS（Hypervisor）/ VS（Virtual Machine）等，進階主題略。

### 1.2 硬體隔離機制

1. **CSR 存取限制**：U-Mode 執行 `csrrw mstatus` 會觸發 Illegal Instruction（cause 2）。S-Mode 連 M-Mode-only 的 CSR 也碰不得。
2. **PMP（Physical Memory Protection）**：以實體位址為單位的保護（M 模式可設記憶體區域可讀/可寫/可執行），U-Mode 被拒可觸發 access fault。
3. **MMU + Page Table（2.2）**：S-Mode 透過 `satp` 設定的核心頁表決定 U-Mode 能見哪些虛擬位址；U 存取被拒 → **Page Fault（cause 12/13/15）**。
4. **特權執行**：U-Mode 無法執行 S/M 才允許的指令（如 `sret`）。

關鍵：U-Mode 無法自行切回高特權——要切**只能靠 `ecall`（軟體陷阱）或硬體中斷**。這正是「唯一入口」的保護。

## 2. 系統呼叫 (Syscall) 執行路徑

### 2.1 使用者端準備

Linux/RISC-V 慣例：

- `a7` = Syscall Number（如 64 = `write`）。
- `a0-a6` = 參數（fd、buffer、length…）。
- 執行 `ecall`。

```asm
.text
.globl _start
_start:
    li   a7, 64          # write
    li   a0, 1           # fd = 1 (stdout)
    la   a1, msg         # buf
    li   a2, 13          # count
    ecall                # ← 硬體介入點！
    li   a7, 93          # exit
    li   a0, 0
    ecall
msg: .ascii "Hello, RISC-V"
```

### 2.2 硬體自動完成的 Trap 序列（ecall）

```
執行 ecall
   1. scause  ← 8 ("Environment call from U-mode")
   2. sepc    ← 當前 PC（ecall 的位址）→ 之後 sret 回此處
   3. stval   ← 可選（此例不需）
   4. sstatus.SPP ← U (記住來源模式)
   5. 特權升至高於 U 的模式（若由 stvec 處理則進 S-Mode）
   6. PC ← stvec 指向的 Traphandler 位址
   7. 進入 S-Mode 開始執行 handler
```

注意：`stvec` 兩模式：
- **Direct**：`stvec = base`，直接跳 handler。
- **Vectored（向量表）**：`stvec = base` 且 handler 按 `cause` 排一個表（中斷使用）。

### 2.3 Handler 工作（S-Mode）

```
trap_vector:
    # Save context
    csrrw sp, sscratch, sp   # 把 user sp 藏進 sscratch，切到 kernel sp
    # （早期用 sscratch 換 sp 再壓 user context）
    addi sp, sp, -REG_SZ     # 產生 kernel stack frame
    sd   a0, OFF_A0(sp)      # 依序存全部 32 個 GPR
    csrr a0, scause          # 讀取原因
    csrr a1, sepc            # 讀取 PC
    call  trap_dispatch      # → 依 cause 分派（用 a0/a1）
    # Restore context
    ld   a0, OFF_A0(sp)      # 還原
    addi sp, sp, REG_SZ
    csrrw sp, sscratch, sp   # 切回 user sp
    sret                     # PC←sepc；特權回 U-Mode
```

## 3. 硬體中斷 (Hardware Interrupts) 與 Trap 處理流程

### 3.1 中斷分類

| 類型 | 同步性 | 例子 |
|------|--------|------|
| **Exception / Fault** | 同步（由指令引起、固定位置） | Illegal Instruction、`ecall`、Page Fault、misaligned |
| **Interrupt** | 非同步（任意時機打斷） | Timer、UART、NVMe DMA 完成 |

兩者合稱 **Trap**——差別在 cause 的**最高位**：`scause[63]=1` → 中斷；=0 → 例外。

### 3.2 中斷來源：CLINT 與 PLIC

- **CLINT（Core Local Interruptor）**：
  - 管理每個 core 的 **Timer Interrupt**（基於 timer compare 機制）與 **Software Interrupt**（核心間 IPI——如讓另一核心重排 task）。
  - 直接以 `mtime`/`mtimecmp` 暫存器比較產生「下一個週期」的 interrupt。
- **PLIC（Platform-Level Interrupt Controller）**：
  - 收集**所有外部設備**（UART、NVMe、GPIO…）的中斷訊號線。
  - 評估**優先權（priority）**與**threshold**——只有高於 threshold 的中斷才會被轉交；支援多個 target（哪些 core 可以接收）。
  - 送出後 wait claim（軟體要先 claim 確認誰被 pending），完成後 completion。

```
外設  ──► PLIC（收集+仲裁+優先權）──► 某個指定 core 的 M/S 中斷匯流排
CLINT ──►（timer/software）──────────► 各 core 私有
        ┌─────────────────────┐
Device ►│ PLIC                │
UART  ►│   priority          │──► Core0 IRQ
NVMe  ►│   threshold         │──► Core1 IRQ
        └─────────────────────┘
```

### 3.3 Trap Handler 執行步驟（三步曲）

```
（假設 S-Mode kernel，收到 Timer 中斷，scause = 0x80000005）

1) SAVE CONTEXT
   trap_vector:
     （切 kernel stack）→ 把所有 GPR 存到 kernel stack frame
     （也保存 ra、sp、部分 CSR 到領域結構）

2) DISPATCH
   讀 scause → 若	 interrupt: 中斷表 vs 例外: syscall/exception 表
   call handle_timer_irq()      → 更新 scheduler tick、排程下一個 process

3) RESTORE & SRET
   自 kernel stack 還原所有 GPR、還原 sepc/sp/sstatus
   sret → 特權回 U-Mode，PC = sepc 繼續使用者執行
```

核心要點：**硬體只做「紀錄+跳轉」**，剩下的 Save / Dispatch / Restore 全由軟體完成——這讓 Trap 的實作極具可攜性，代價是軟體要極度小心 push/pop 對稱。

## 4. 上下文切換 (Context Switch) 的硬體開銷分析

### 4.1 微架構直接開銷（由 trap 本身）

- 保存/還原 **32 個通用暫存器 + 若干 CSR + sp**：以流水線看待，約為數百 cycles（存取 kernel stack、load/store 延遲）。
- 切換 `satp`（若是 process switch）會 invalidate TLB（除非用 ASID）。
- 來自「例外後管線 flush」的費用：OoO 需回滾 precond。（1.4 節）

### 4.2 微架構間接開銷（最貴的部分！)

| 項目 | 影響 |
|------|------|
| **TLB Flush**（換 `satp`） | 下次存取每個新 VA 都得重新 walk 頁表（多層、數百 cycles）——即使資料還在 cache |
| **Cache Cold Misses** | 新 process 載入 → L1/L2 命中率瞬間崩跌（Compulsory + Capacity miss，2.1 節 3C 模型）——正是 4.2 最昂貴的效能懲罰 |
| **Branch Predictor 失效** | 預測器的 GHR/BHT 屬「舊 process」，切換後失準率上升數餘倍 |
| **TB 回寫（VIPT alias 等）** | 微小但累積 |

**量化**：一個空 context switch 在現代伺服器上約 1–5 µs；但其中「新 process 的 cold TLB+cache」可能要數百到數千 cycles 才能回血。OS 的調度器用了很多技巧（per-core runqueue、CPU affinity、process 的 locality）來減少 context switch 次數——這正是微架構對 OS 設計的反饋。

### 4.3 ASID 的價值（回顧 2.2）

有了 ASID（Address Space ID），換 `satp` 不必整批 flush TLB——同一 TLB 同時保留多個 process 的 entry，跨切換後立刻可用。但若 TLB 容量小，多 process 互踢仍免不了。

## 5. 完整心流圖（一次 U→S→U 的中斷）

```
                ┌── ecall ──────────────►┐
   U-Mode       │  scause=8  sepc=PC      │
   application ─┘  sret (PC←sepc)         ▼
                                        S-Mode (kernel)
                     trap_vector：save → dispatch → restore → sret
```

```
                ┌── Timer interrupt ─────►┐
   U-Mode       │  scause=0x80000005       │
   running ─────┘  sret (軟體處理後)        ▼
                                        S-Mode (kernel)
                     handle_timer_irq() → scheduler → context switch → sret
```

## 6. 小結

- 特權模型 U/S/M：最低 U 只能靠 `ecall` 或中斷提升。
- Syscall = `a7`+`a0-a6` + `ecall` → 硬體填 `scause/sepc/sstatus`，跳 `stvec`。
- CLINT 管 timer/software IPI；PLIC 管外部設備；cause 最高位區分中斷/例外。
- Trap Handler 三步曲：Save → Dispatch → Restore → `sret`。
- Context Switch 的真正成本是 **TLB Flush + Cache Cold**，遠超過暫存器存取本身；ASID 是減輕 TLB 懲罰的關鍵技巧。

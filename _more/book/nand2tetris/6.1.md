## 前言

在前面幾章，我們親手打造了邏輯閘、ALU、記憶體，最後組出了整台 Hack 電腦。但到目前為止，這台電腦只懂一件事：**一串 16 位元的 0 與 1**。你要它執行加法，就得把 `1110000010000000` 這種東西餵給它。可是人類不是這樣溝通的——我們習慣寫 `D = M + 1`，而不是 `0001110000010010`。

## 1. 組譯器的角色：把 .asm 變成 .hack

先看一張總覽圖。Hack 電腦的軟硬體交界長這樣：

```
    sum.asm（組合語言文字檔）
            │
            ▼
   ┌──────────────────────┐
   │       組譯器         │
   │      Assembler       │
   └──────────────────────┘
            │
            ▼
    sum.hack（16 位元機器碼文字檔）
            │
            ▼
    ROM / CPU 模擬器執行
```

組譯器接受一個副檔名為 `.asm` 的文字檔，經由「讀取 → 清理 → 解析 → 翻譯」四道工序，產出一個 `.hack` 文字檔。每一行 `.hack` 都是一個 16 位元的二進位字串，例如：

```asm
// sum.asm（第 5 行）
D=M
```

```text
// sum.hack（對應的第 5 行）
1111110000010000
```

請注意一個關鍵事實：**`.hack` 檔案本質上仍是文字檔**。真正的「機器碼」是那些 0 與 1 所代表的電壓位準，而 `.hack` 只是把它們「用文字記載下來」的媒介。CPU 模擬器（或我們在第 5 章做的 ROM）逐行讀取這些位元，餵給硬體執行。

### 1.1 組譯器 vs. 高階語言編譯器

組譯器是所有編譯器中最單純的一種。它的單純來自一個事實：

> **每一條組合語言指令，恰好對應一條機器碼指令。**

這與高階語言截然不同。C 語言的一行 `sum = sum + i;` 會被編譯成一整串平行的、高度優化的、使用多種暫存器的機器碼，而且結果可能因編譯器版本而異。組譯器沒有這個自由度——`D=M` 在 Hack 上就只有一種正確的編碼。

| 特性 | 組譯器 | 高階語言編譯器 |
|------|--------|----------------|
| 對應關係 | 一對一 | 一對多 |
| 語法規則 | 極簡（幾種形式） | 複雜（文法、型別、作用域） |
| 翻譯結果 | 幾乎唯一 | 優化空間巨大 |
| 難度 | 一週可完成 | 數年工程量（如 GCC） |

理解組譯器，是理解一切編譯技術的地基。本章完成了它，第 10、11 章的真正編譯器才有意義。

## 2. .asm 與 .hack 的一對一對應

Hack 機器語言只有**兩種指令**，所以組譯器的工作被大幅簡化：

| 指令類型 | 語法 | 機器碼格式 | 用途 |
|----------|------|------------|------|
| A-指令 | `@value` | `0` + 15 位元位址 | 設定 A 暫存器（載入常數或位址） |
| C-指令 | `dest=comp;jump` | `111` + 7+3+3 位元 | 運算、寫入暫存器/記憶體、跳躍 |

「一對一」的意思具體來說是：`.asm` 中**每一條真正的指令**（扣除註解、空行、標號），在 `.hack` 中都有**一行位元串**與之對應；行號與行號依次對齊。我們在 6.3 節實作組譯器時，會反覆利用這個性質來決定標號位址。

### 2.1 一個最樸素的例子

先看一段最簡單的組合語言，它只用 A-指令：

```asm
// a.asm：把 7 載入 A 暫存器
@7
D=A       // 等等，D=A 是 C-指令
```

別急，我們一次只看第一步。把 `@7` 翻成機器碼很直覺：

- 機器碼格式規定：A-指令的第 0 位（最高位）固定為 `0`；
- 剩餘 15 位拿來放「值 7」的二進位表示。

```
@7   →   0 000000000000111
```

因為 7 的二進位是 `111`（佔 3 位），前面補足 12 個 0，湊成 15 位，再接在開頭的 `0` 之後，共 16 位：

```
0000000000000111
```

這就是 `@7` 唯一合法的 `.hack` 編碼。靠著這個「第一位是 0」的特性，CPU 可以立刻分辨 A-指令與 C-指令——這是硬體第 4、5 章就設計好的事。

## 3. A-指令的轉譯

A-指令的統一語法與對應格式：

```
語法:   @value
格式:   0 aaaaaaaaaaaaaaa     （最高位 0 + 15 位元無號整數 value）
```

其中 `value` 可以是：

1. **非負十進位常數**：`@7`、`@32767`
2. **符號**：`@R0`、`@SCREEN`、`@LOOP`、`@i`（符號會由符號表解析成位址，見 6.2 節）

無論哪一種，翻譯出來都是同一個動作：把那個數值放到 A 暫存器。用 Python 可以寫成一行：

```python
def encode_a(value: int) -> str:
    """把 0 <= value < 2^15 的整數編成 16 位元 A-指令機器碼"""
    return '0' + f'{value:015b}'
```

測試幾個例子：

| `@value` | value 二進位（15 位） | 完整機器碼 |
|----------|-----------------------|------------|
| `@0` | `000000000000000` | `0000000000000000` |
| `@7` | `000000000000111` | `0000000000000111` |
| `@21` | `000000000010101` | `0000000000010101` |
| `@16384` (SCREEN) | `100000000000000` | `0100000000000000` |
| `@32767` | `111111111111111` | `0111111111111111` |

> **設計思路**：為什麼 A-指令要花掉最高的 1 個位元當「旗標」？因為 CPU 在每個週期第一件事就是要判斷「這是哪種指令」。用最高位當旗標，加一條 Mux 就能分出兩路——這是犧牲一半位址空間（只剩 15 位、0~32767）換取硬體極簡的經典取捨。回想第 5 章的 CPU：`instruction[15]` 這條線，正是那個判斷開關。

## 4. C-指令的轉譯

C-指令才是 Hack 電腦的「運算引擎」。它同時可以做三件事：

```
語法:   dest = comp ; jump     （其中 = 與 ; 二者皆為可選）
格式:   111 a ccccccc ddd jjj
        └┬┘ │ └──┬──┘ └┬┘ └┬┘
        前綴  a位元 計算 存放 跳躍
```

拆開來看：

| 欄位 | 位元寬 | 功能 |
|------|--------|------|
| `111` | 3 | 固定前綴，標記「這是 C-指令」 |
| `a` | 1 | 選擇 A 或 M 作為運算元（`a=0` 用 A，`a=1` 用 M） |
| `ccccc c` | 6 | comp：執行哪一種運算 |
| `ddd` | 3 | dest：結果寫到哪裡 |
| `jjj` | 3 | jump：依運算結果決定是否跳躍 |

### 4.1 一張表就解決：全部的 comp 碼

Nand2Tetris 的神奇之處，是 CPU 的 ALU（第 2 章）幾乎把「能算的」都算完了：0、1、-1、D、A、!D、!A、-D、-A、D+1、A+1、D-1、A-1、D+A、D-A、A-D、D&A、D|A。C-指令的 comp 欄位只是「從中選一個」。

`a=0` 時的 comp 編碼：

| comp 助記 | c 位元（6 位） | 完整 comp 欄位（含 a=0） |
|-----------|---------------|--------------------------|
| `0`     | `101010` | `0101010` |
| `1`     | `111111` | `0111111` |
| `-1`    | `111010` | `0111010` |
| `D`     | `001100` | `0001100` |
| `A`     | `110000` | `0110000` |
| `!D`    | `001101` | `0001101` |
| `!A`    | `110001` | `0110001` |
| `-D`    | `001111` | `0001111` |
| `-A`    | `110011` | `0110011` |
| `D+1`   | `011111` | `0011111` |
| `A+1`   | `110111` | `0110111` |
| `D-1`   | `001110` | `0001110` |
| `A-1`   | `110010` | `0110010` |
| `D+A`   | `000010` | `0000010` |
| `D-A`   | `010011` | `0010011` |
| `A-D`   | `000111` | `0000111` |
| `D&A`   | `000000` | `0000000` |
| `D\|A`  | `010101` | `0010101` |

`a=1` 時（把 M 當成 A 用），comp 欄位差在一開始：

| comp 助記 | 完整 comp 欄位（含 a=1） |
|-----------|--------------------------|
| `M`     | `1110000` |
| `!M`    | `1110001` |
| `-M`    | `1110011` |
| `M+1`   | `1110111` |
| `M-1`   | `1110010` |
| `D+M`   | `1000010` |
| `D-M`   | `1010011` |
| `M-D`   | `1000111` |
| `D&M`   | `1000000` |
| `D\|M`  | `1010101` |

**記憶技巧**：`M` 相關的編碼，就是把 `A` 相關編碼的 `a` 位元（第 4 位，從右數）由 0 改成 1。硬體上，M 就是「A 所指向的記憶體」，所以 CPU 只需把 `Memory[A]` 餵給 ALU 而不用重造運算邏輯——這就是為什麼把 ML 設定成與 A 同組運算非常划算。

### 4.2 dest 欄位：結果寫到哪

| dest 助記 | ddd | 寫入位置 |
|-----------|-----|----------|
| （省略） | `000` | 不寫任何地方 |
| `M`  | `001` | 記憶體 `Memory[A]` |
| `D`  | `010` | D 暫存器 |
| `MD` | `011` | D 與記憶體 |
| `A`  | `100` | A 暫存器 |
| `AM` | `101` | A 與記憶體 |
| `AD` | `110` | A 與 D |
| `AMD`| `111` | A、D 與記憶體全部 |

注意 dest 的 3 個位元，**每一位都是一個獨立的「寫入開關」**：第 1 位管 M、第 2 位管 D、第 3 位管 A。因此組譯器只要查表即可，沒有組合邏輯。

### 4.3 jump 欄位：何時跳

| jump 助記 | jjj | 跳躍條件 |
|-----------|-----|----------|
| （省略） | `000` | 不跳 |
| `JGT` | `001` | 若 `comp > 0` |
| `JEQ` | `010` | 若 `comp = 0` |
| `JGE` | `011` | 若 `comp >= 0` |
| `JLT` | `100` | 若 `comp < 0` |
| `JNE` | `101` | 若 `comp != 0` |
| `JLE` | `110` | 若 `comp <= 0` |
| `JMP` | `111` | 無條件跳 |

硬體邏輯（第 5 章）是：ALU 的輸出（comp 的結果）同時送到三個標誌偵測器 `zr`（零）、`ng`（負），再與 jump 欄位比對，決定下一個 PC 要不要變成 `A`。跳或不跳，都寫死在硬體裡了。

### 4.4 用 Python 查表轉譯 C-指令

實作時，我們把這幾張表直接寫成 Python 字典，翻譯就是「查表 + 拼接字串」：

```python
COMP = {
    '0':'0101010','1':'0111111','-1':'0111010','D':'0001100','A':'0110000',
    '!D':'0001101','!A':'0110001','-D':'0001111','-A':'0110011',
    'D+1':'0011111','A+1':'0110111','D-1':'0001110','A-1':'0110010',
    'D+A':'0000010','D-A':'0010011','A-D':'0000111','D&A':'0000000','D|A':'0010101',
    'M':'1110000','!M':'1110001','-M':'1110011','M+1':'1110111','M-1':'1110010',
    'D+M':'1000010','D-M':'1010011','M-D':'1000111','D&M':'1000000','D|M':'1010101',
}

DEST = {'':'000','M':'001','D':'010','MD':'011','A':'100','AM':'101','AD':'110','AMD':'111'}

JUMP = {'':'000','JGT':'001','JEQ':'010','JGE':'011','JLT':'100','JNE':'101','JLE':'110','JMP':'111'}

def encode_c(line: str) -> str:
    """把 dest=comp;jump 譯成 16 位元 C-指令"""
    dest = ''
    comp = line
    jump = ''
    if ';' in line:                    # 拆 jump
        comp, jump = line.split(';')
    if '=' in line:                    # 拆 dest
        dest, comp = comp.split('=')
    return '111' + COMP[comp] + DEST[dest] + JUMP[jump]
```

### 4.5 手算幾個例子

**例子一：`D=A`（載入常數到 D）**

```
dest = D → ddd = 010
comp = A → a=0, c=110000 → comp 欄位 = 0110000
jump = 無 → 000

結果：111 0110000 010 000 = 1110110000010000
```

**例子二：`M=D+M`（記憶體累加，迴圈常用）**

```
dest = M → 001
comp = D+M → a=1 → 1000010
jump = 無

結果：111 1000010 001 000 = 1111000010001000
```

**例子三：`D;JGT`（大於零就跳，迴圈判斷）**

```
dest = 無 → 000
comp = D → 0001100
jump = JGT → 001

結果：111 0001100 000 001 = 1110001100000001
```

> **設計思路**：注意例三，`D;JGT` 的「計算」就是 `D` 本身——我們並沒有真的「運算」什麼，只是把 D 的值餵給跳躍判斷器。這就是 Nand2Tetris 的精巧：**jump 只是把 ALU 的輸出拿來當條件用**，所以「比較後跳躍」不需要額外的指令形態。

## 5. 從符號到數值：位址的化身

前面我們看到的 `.asm` 全都乖乖寫數值（`@7`、`@16384`）。但真實程式幾乎不會這樣寫——你會寫 `@i`、`@sum`、`@LOOP`，而不是死背位址 16、17、18。於是組譯器多了一項核心任務：

> **把符號（symbol）解析成數值位址。**

`@value` 中 `value` 的三種可能，對應三種處理：

| `value` 的形式 | 例 | 處理方式 |
|---------------|-----|----------|
| 純數字（10 進位） | `@7` | 直接轉成 15 位元二進位 |
| 預定義符號 | `@R1`、`@SCREEN` | 查表取得固定位址 |
| 使用者定義符號 | `@i`、`@LOOP`、`@END` | 用符號表在組譯期間配置位址 |

舉例，當組譯器看到 `@SCREEN`：

- 查符號表得知 `SCREEN = 16384`（螢幕記憶體映射基地）；
- 於是轉譯成 `0100000000000000`（16384 的 15 位元 = `100000000000000`）。

有關符號表的三類符號如何產生、如何配置位址，是 6.2 節的主題。在本節你可以先把「符號解析」看成一個黑盒子：**組譯器保證每一支符號最後都變成一個 15 位元內的非負整數**。

## 6. 多位元組碼的組成：16 位元的鑲嵌

把一切都攤開來看，Hack 的唯一字長是 **16 位元**。A-指令與 C-指令占據了其中「由最高位開始」的所有空間，兩者涇渭分明：

```
A-指令（16 位元）:
         ┌── 15 位元位址 ──┐
   0 a a a a a a a a a a a a a a a

C-指令（16 位元）:
   ┌┴┐ ┌┬┐ ┌── 6 位元 ──┐ ┌┤┌┐┌┤┌┐
   1 1 1 a c c c c c c d d d j j j
   111   a    comp        dest jump
```

這兩種格式合起來共有 `2^16 = 65536` 種組合。種類多不到哪去——但這正是這台「極簡電腦」的本意，讓你每一塊位元都知道它在做什麼。

### 6.1 組譯器的輸出規格

`.hack` 檔案有嚴格的輸出規範，方便 CPU 模擬器逐行讀取：

1. 每一行恰是一個 16 位元的二進位字串；
2. 每行結尾以換行符號 `\n` 結束（最後一行也建議補上）；
3. 內容只能是 `0`、`1` 與換行，不得含有空格、註解。

### 6.2 位元組（byte）的迷思：為什麼是 16 位元？

電腦術語常說「8 位元 = 1 byte」，那 Hack 的 16 位元算什麼？無法定義——因為 Hack 記憶體的最小可定址單位就是 16 位元。這告訴我們一個重要事實：

> 「位元組」不是宇宙定律，而是**指令集設計的決定**。Hack 選擇 16 位元字長，是因為它要同時容納 A-指令的 15 位元位址空間（0~32767，足以涵蓋 RAM16K 與螢幕/鍵盤映射）與 C-指令的完整運算欄位。

若你日後學 RISC-V（32 位元）、x86（8 位元位元組），會看到完全不同的字長取捨。

## 7. 組譯器整體管線：讀取、清理、解析、翻譯

把本節所有概念串起來，一個組譯器就是下面這條管線。我們在第 6.3 節會把它全部變成可執行的 Python 程式，這裡先看骨架：

```
         .asm 原始檔
              │
        ┌─────▼─────┐
   (1)  │  讀取檔案  │  逐行讀入文字，保存行號順序
        └─────┬─────┘
              │
        ┌─────▼─────┐
   (2)  │  清理內容  │  去除白空格 + 去除 // 註解 + 跳過空行 + 辨識 (標號)
        └─────┬─────┘
              │
        ┌─────▼─────┐
   (3)  │  解析指令  │  判斷是 A-指令還是 C-指令；拆解 dest/comp/jump；查/配符號
        └─────┬─────┘
              │
        ┌─────▼─────┐
   (4)  │  翻譯編碼  │  依格式拼出 16 位元機器碼字串
        └─────┬─────┘
              │
        ┌─────▼─────┐
   (5)  │  寫出檔案  │  每行一個 16 位元字串，存成 .hack
        └───────────┘
```

把這五步用 Python 寫成主程式骨架，幾乎就是完整組譯器的雛形：

```python
import sys

def assemble(source: str) -> list[str]:
    lines = read_lines(source)      # (1) 讀取
    cleaned = clean_lines(lines)    # (2) 清理
    parsed = parse_instructions(cleaned)  # (3) 解析 + (4) 翻譯
    return parsed
```

> **設計思路**：這個管線最關鍵的設計決策是**「清理」必須發生在任何位址計算之前**。為什麼？因為標號位址是「第幾條指令」決定的，而註解、空行、`(標號)` 本身都不算指令——若在數行號時把它們算進去，所有位址就全錯了。這個「數行號」的細節正是 6.3 節兩階段掃描的核心動機。

## 8. 本章小結

- 組譯器是**軟體與硬體之間的第一道橋樑**，把 `.asm` 轉成 `.hack`；因為一對一對應，它是「最容易拿來教學的編譯器」。
- A-指令 `@value` 譯為 `0` + 15 位元位址，CPU 靠最高位判斷指令種類。
- C-指令 `dest=comp;jump` 譯為 `111` + `a` + 6 位元運算 + 3 位元目的地 + 3 位元跳躍，全部的組合都收錄在三張表（COMP / DEST / JUMP）裡。
- 符號是位址的化身，組譯器必須把符號解析成數值才算完成翻譯。
- 組譯器整體管線為：**讀取 → 清理 → 解析 → 翻譯 → 輸出**；「清理先行、再數位址」是正確性的關鍵。

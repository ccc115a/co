# 11.1 LLM 推理瓶頸：Prefill 階段（Compute-Bound）與 Decode 階段（Memory-Bound）

## LLM 推理基礎

### Transformer 推理流程

```
LLM 推理兩階段：
┌─────────────────────────────────────────────────┐
│  輸入序列                                       │
│  "今天天氣如何？"                               │
│      ↓                                          │
│  ┌──────────────────────────────────────────┐   │
│  │  1. Prefill（預填充）                   │   │
│  │     - 處理整個輸入序列                │   │
│  │     - 平行計算（一次處理所有 token）   │   │
│  │     - 計算密集（Compute-Bound）        │   │
│  │     - 產生第一個輸出 token 與 KV Cache  │   │
│  └──────────────────────────────────────────┘   │
│      ↓                                          │
│  ┌──────────────────────────────────────────┐   │
│  │  2. Decode（解碼）                     │   │
│  │     - 逐 token 產生輸出                │   │
│  │     - 一次只算一個 token（串行）       │   │
│  │     - 記憶體密集（Memory-Bound）        │   │
│  │     - 每次輸出一個字                │   │
│  └──────────────────────────────────────────┘   │
│      ↓                                          │
│  輸出序列                                       │
│  "今天天氣晴朗…"                                │
└─────────────────────────────────────────────────┘
```

### 兩階段的差異

```
Prefill vs Decode 比較：
┌─────────────────────────────────────────────────┐
│  特性      │  Prefill        │  Decode          │
├─────────────────────────────────────────────────┤
│  處理數量  │  整個序列       │  單一 token     │
│  平行度    │  高（可平行）   │  低（串行）     │
│  計算量    │  大             │  小             │
│  記憶體量  │  中             │  大（KV 讀取）  │
│  瓶頸類型  │  計算（Compute）│  記憶體（Memory）│
│  時間      │  一次較長       │  多次短         │
│  佔比      │  小部分時間     │  大部分時間     │
└─────────────────────────────────────────────────┘
```

## Prefill 階段深入分析

### Prefill 特性

```
Prefill 計算：
┌─────────────────────────────────────────────────┐
│  第 t 層的計算：                                │
│                                                  │
│  Attention：                                     │
│  Q = X × WQ                                    │
│  K = X × WK                                    │
│  V = X × WV                                    │
│  Output = softmax(Q × K^T / √d) × V            │
│                                                  │
│  FFN（前饋網路）：                               │
│  Output = GELU(X × W1) × W2                    │
│                                                  │
│  輸入 X：形狀 (sequence_length, hidden_size)     │
│  例：(2048, 4096)                             │
│                                                  │
│  計算量：                                        │
│  ~2 × seq_len × hidden × weight                │
│  seq_len 越長，計算越多                    │
└─────────────────────────────────────────────────┘
```

### Prefill 為何是 Compute-Bound

```
Prefill 計算受限原因：
┌─────────────────────────────────────────────────┐
│  1. 大矩陣乘法                                │
│     - 輸入長（整個序列）                     │
│     - GEMM 計算量大                           │
│                                                  │
│  2. 高平行度                                  │
│     - 所有 token 同時處理                   │
│     - GPU 算力充分利用                       │
│                                                  │
│  3. 計算密度高                              │
│     - 每資料的計算量多                    │
│     - 能塞滿計算單元                      │
│                                                  │
│  結果：                                          │
│  - 瓶頸是 FLOPs                                │
│  - 提升算力可直接加速                        │
│  - Tensor Core 是關鍵                        │
└─────────────────────────────────────────────────┘
```

### Prefill 優化

```
Prefill 優化策略：
┌─────────────────────────────────────────────────┐
│  1. 增大算力利用率                              │
│     - 使用大 GEMM 分塊                     │
│     - 使用 Tensor Core                    │
│     - 維持高計算熱（Arithmetic Intensity）  │
│                                                  │
│  2. 平行化                                    │
│     - 多 GPU 張量平行                      │
│     - 分割序列                              │
│                                                  │
│  3. FlashAttention                          │
│     - 避免大 Attention 矩陣（O(N²)）       │
│     - 計算與記憶體折衷                   │
│                                                  │
│  4. 減少計算                                  │
│     - 量化到低精度（FP8）                 │
│     - 稀疏支援                            │
└─────────────────────────────────────────────────┘
```

## Decode 階段深入分析

### Decode 特性

```
Decode 計算：
┌─────────────────────────────────────────────────┐
│  新 token 的計算：                              │
│                                                  │
│  Attention：                                     │
│  q_new = x_new × WQ     ← 小計算             │
│  k_new = x_new × WK                            │
│  v_new = x_new × WV                            │
│                                                  │
│  與所有歷史 KV 比較：                          │
│  score = q_new × K^T                          │
│  # K 是整個歷史序列的鍵                        │
│  # 每次只算一個新 token                      │
│                                                  │
│  output = softmax(score) × V                  │
│                                                  │
│  計算量：                                        │
│  - 矩陣乘法小（1×d 乘 d×d）                 │
│  - 但需要讀取所有歷史 KV（巨大）         │
└─────────────────────────────────────────────────┘
```

### Decode 為何是 Memory-Bound

```
Decode 記憶體受限原因：
┌─────────────────────────────────────────────────┐
│  1. KV Cache 讀取                              │
│     - 每個新 token 需讀取所有歷史 KV   │
│     - 歷史越長，讀取越多          │
│                                                  │
│  2. 單一 token 平行度低                        │
│     - 矩陣很小（1×d）                     │
│     - 無法充分利用計算單元              │
│                                                  │
│  3. 計算密度低                              │
│     - 每資料的計算少                │
│     - 受限於記憶體頻寬                  │
│                                                  │
│  4. 權重參數讀取                              │
│     - 需要載入整個模型權重（百GB）     │
│     - 每次推理都要讀                    │
│                                                  │
│  結果：                                          │
│  - 瓶頸是記憶體頻寬                          │
│  - 提升算力幫助有限                        │
│  - 增加頻寬/減少記憶體量是關鍵    │
└─────────────────────────────────────────────────┘
```

### Decode 的記憶體瓶頸計算

```
Decode 頻寬需求分析：
┌─────────────────────────────────────────────────┐
│  範例（7B 模型）：                                 │
│                                                  │
│  - 模型參數：7B 約 14 GB（FP16）               │
│  - KV Cache：每次讀取約數 GB                   │
│                                                  │
│  每次 token 產出需讀取的記憶體：                 │
│  = 權重（14GB）+ KV Cache                      │
│  ≈ 15-20 GB                                   │
│                                                  │
│  記憶體頻寬需求：                                │
│  - 若目標 100 tokens/s                        │
│  - 需要頻寬：15 GB × 100 = 1.5 TB/s           │
│                                                  │
│  計算需求：                                   │
│  相比記憶體需求，計算需求很小             │
│  → Memory-Bound                               │
└─────────────────────────────────────────────────┘
```

## 兩階段的效能測量

### 效能指標

```
LLM 推理關鍵指標：
┌─────────────────────────────────────────────────┐
│  1. TTFT（Time To First Token）                │
│     - 從請求到第一個輸出 token 的時間          │
│     - 主要受 Prefill 影響                  │
│     - 用戶感知的「響應」速度         │
│                                                  │
│  2. TPOT（Time Per Output Token）              │
│     - 每個輸出 token 的時間                 │
│     - 主要受 Decode 影響                │
│                                                  │
│  3. Throughput（吞吐量）                       │
│     - 每秒完成的輸出 token 數            │
│     - 整體處理量                      │
│                                                  │
│  4. Latency（端到端延遲）               │
│     - TTFT + TPOT × 輸出長度              │
└─────────────────────────────────────────────────┘
```

### 兩階段時間分佈

```
時間分佈：
┌─────────────────────────────────────────────────┐
│  典型情況（輸出 100 token）：                     │
│                                                  │
│  Prefill（輸入 512 token）：~30 ms             │
│  Decode（100 token × 20ms）：~2000 ms         │
│                                                  │
│  Decode 佔了大部分時間（~98%）                │
│                                                  │
│  意義：                                          │
│  - 優化 Decode 對吞吐量關鍵                  │
│  - 優化 Prefill 對 TTFT（響應速度）關鍵  │
└─────────────────────────────────────────────────┘
```

## 優化策略總覽

### Prefill 優化

```
Prefill 優化重點：
┌─────────────────────────────────────────────────┐
│  目標：降低 TTFT                              │
│                                                  │
│  方法：                                          │
│  1. 提升算力（Tensor Core、多 GPU）          │
│  2. 批次多個請求（增大 GEMM）              │
│  3. FlashAttention（避免 O(N²)）           │
│  4. 低精度（FP8/BF16）                       │
│  5. 提早退出（Early Exit，可選）             │
└─────────────────────────────────────────────────┘
```

### Decode 優化

```
Decode 優化重點：
┌─────────────────────────────────────────────────┐
│  目標：提升吞吐量                              │
│                                                  │
│  方法：                                          │
│  1. 批次處理（Batch）：                        │
│     - 多個請求共享權重讀取                    │
│     - 提升權重重用率                    │
│                                                  │
│  2. KV Cache 壓縮：                           │
│     - 量化 KV Cache                         │
│     - 共享（MLA，如 DS/DeepSeek）          │
│                                                  │
│  3. PagedAttention：                         │
│     - 管理 KV Cache 記憶體                │
│     - 減少碎片                          │
│                                                  │
│  4. 減少權重讀取：                          │
│     - 權重量化                          │
│     - 模型平行                          │
└─────────────────────────────────────────────────┘
```

## 批次與兩階段

### 不同階段的批次策略

```
Prefill/Decode 批次：
┌─────────────────────────────────────────────────┐
│  Prefill 批次：                                  │
│  - 合併多個請求的 Input                      │
│  - 形成更大的 GEMM                      │
│  - 提升算力利用率                        │
│                                                  │
│  Decode 批次：                                   │
│  - 合併多個請求的單一 token                  │
│  - 共享權重讀取              │
│  - 提升記憶體利用率                │
│                                                  │
│  ┌──────────────────────────────────────────┐   │
│  │  批次大小        │  影響                 │   │
│  │  小（1）         │  低吞吐量             │   │
│  │  中（8-32）      │  平衡                 │   │
│  │  大（64+）       │  高吞吐量但延遲高     │   │
│  └──────────────────────────────────────────┘   │
└─────────────────────────────────────────────────┘
```

## 本章小結

- LLM 推理分為 Prefill 與 Decode 兩個階段
- Prefill 處理整個輸入序列，計算密集（Compute-Bound）
- Decode 逐 token 產生輸出，記憶體密集（Memory-Bound）
- Prefill 瓶頸是算力，可透過 Tensor Core 加速
- Decode 瓶頸是記憶體頻寬，需減少記憶體讀取
- TTFT 受 Prefill 影響，吞吐量受 Decode 影響
- 批次、KV Cache 壓縮、量化是關鍵優化技術

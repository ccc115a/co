## 1. 為什麼需要虛擬記憶體？

### 1.1 三大動機

1. **隔離（Isolation）**：每個 Process 擁有私有位址空間，不能互相窺視或覆寫；OS 核心受保護（特權層級見 4.2）。
2. **抽象與重定位**：程式只需假設「我的 0x1000 是寬鬆的」，實體位置由 OS 擺。
3. **無界位址空間**：實體記憶體不夠時（如程式要 8GB、機器只有 4GB），OS 可把部分頁面置於磁碟（Swap）——程式無感。

虛擬記憶體的核心機制是**分頁（Paging）**：把虛擬位址空間（VA）與實體位址空間（PA）都切割成**固定大小的頁面（Page）**，通常 4KB。OS 維護**頁表（Page Table）**── 每頁一個「VA→PA + flag」的對映項。

### 1.2 名詞速記

| 名詞 | 全名 | 說明 |
|------|------|------|
| VA / PA | Virtual / Physical Address | 虛擬 / 實體位址 |
| PTE | Page Table Entry | 一個頁的對映項：PFN + flags |
| PFN | Page Frame Number | 該頁在實體記憶體的位置 |
| V      | Valid bit | PTE 是否有效（1=在 DRAM，0=在 swap 或不存在） |
| R/W/X | 讀/寫/執行權限 |
| A/D   | Accessed/Dirty | 供 OS 做 LRU、swap 回寫管理 |
| U     | User accessible | U-Mode 可否存取 |
| ASID | Address Space ID | 標記一片 TLB entry 屬於哪個 Process |

## 2. 頁表 (Page Table) 結構與多層轉譯

### 2.1 單層頁表（問題）

32-bit 位址、4KB 頁 → 需 $2^{32-12} = 2^{20} = 1M$ 個 PTE。若每個 PTE 4 bytes → **單層頁表就要 4 MB 常駐 DRAM**。每個 process 都有一份！4GB 位址空間可能被 4MB 頁表吃掉 0.1%，且是**連續常駐**——浪費且 cold。

### 2.2 多層頁表（解）

把 VA 拆成多級 Index（RV32 用 2 級、RV64 用 3–4 級），**只有被用到的下層頁表才實體存在**：

```
VA (32-bit, Sv32):  [ VPN[1] 10b ][ VPN[0] 10b ][ offset 12b ]
                      │             │            └── 4KB
                      ▼             ▼
      satp ──► Root PTE(1) ──► PTE(0) ──► Page
              （頂層表，1 entry/4KB）
```

- 頂層（Root）表永遠存在。
- 下層表**按需建立**：未被觸及的區域（如稀疏的 heap 高位）不建任何 PTE。
- 對於固定位置的資料（如 text/stack）共用少數幾頁底下層表。

**位址空間大型稀疏程式節省的空間、以時間（多級索引）換來。** 典型 trade-off。

### 2.3 RISC-V Sv39 三層轉譯（示範）

Rv64 的 39-bit VA（39 bits VA = 512 GiB，取自 64 位的高 39 bits）：

```
VA[38:30] -> Level 2 page table      (VPN[2], 9 bits)
VA[29:21] -> Level 1 page table      (VPN[1], 9 bits)
VA[20:12] -> Level 0 page table      (VPN[0], 9 bits)
VA[11:0]  -> Offset within 4KB page  (12 bits)
```

每層 512 個 PTE（每 PTE 8 bytes → 一頁 4KB 表）。轉譯流程：

1. `satp`（S-Mode CSR）提供 **Root（L2）表** 的實體位址。
2. `PTE_L2 = Root + (VPN[2] × 8)`；讀出看 `V/R/W/X`（若無效 → Page Fault）。
3. 該 PTE 指向 L1 表；`PTE_L1 = L1_base + (VPN[1] × 8)` → 得 L0 表。
4. `PTE_L0 = L0_base + (VPN[0] × 8)` → 得最終 **PA = PFN | offset**。

若任一層 PTE 的 **V=0**（或權限不符），即 **Page Fault**。頁表「多層沉底」可以**只分配需要的下層表**——最實際的節約。

### 2.4 Page Fault 處理（OS 責任）

1. **MMU/硬體偵測**：load 的 VA 轉譯走到「無效 PTE / 權限違反」→ 觸發例外（RISC-V `mcause`/`scause` = Page Fault），`sepc` 記下發生位址，`mtval/stval` 帶該 VA。
2. **OS handler**（4.2 節的 trap 路徑之一）：
   - 若頁在 swap：從磁碟讀回 DRAM 的閒置框；
   - 更新 PTE（Valid=1、PFN）。
3. **回寫 PTE 後重新執行**原指令（`sret` 回 `sepc`）。

**實現細節**：Page Fault handler 執行的時候**不能再去碰頁表**（自己的頁表也在 swap）——OS 需保證 kernel 頁面永不 swap out（pinning）。

## 3. 轉譯後備緩衝區 (TLB) 運作

### 3.1 為何需要 TLB

多層頁表的轉譯**每筆 load/store 都要 3–4 次 DRAM 讀取**——代價遠大於 cache miss 本身。因此 CPU 用 **TLB（Translation Lookaside Buffer）**：一張**全相聯/組相聯的小型高速 cache**，快取最近用的「VA→PA」對映（PTE）。

- 容量小（通常 64–512 entries）。
- 因為只用來存「轉譯」，不存資料內容本身——所以全相聯的功耗也能負擔。

### 3.2 TLB Hit / Miss 行為

- **Hit**：直接拿到 PA，進行 Cache 索引。TLB hit 可與 L1 存取**平行**（見 VIPT）。
- **Miss**：需進行完整的多層頁表 walk。**硬體 walk**（x86、ARM、RISC-V 有 `Zicbom` 等支援）或 **軟體 walk**（早期 MIPS 由 OS 載入 `lw` + `tlbwr`）。硬體 walk 較普遍。
  - Walk 的頁表本身可被 Cache 快取（Page Table walker 有自己的小 cache，Cache PTEs）。
- **Fill**：walk 所得 PTE 填入 TLB。

### 3.3 TLB 失效 (Flush) 與 ASID

切換 Process（換頁表 = 更新 `satp`）時，**若不標記 Process**，TLB 內的對映會「跨 process 洩漏」——所以：

- **全部 flush**：每次 context switch 清空 TLB（TLB miss 重新 walk，效能懲罰）。
- **ASID（Address Space ID）**：TLB entry 加標記該 Process 的 ID（如 `satp.ASID`）。hit 需比對 Tag + ASID；不同 process 的 entry **並存不互相衝突**——context switch 時 TLB 不必 flush，省下巨額懲罰。

SWAP 回寫 / 頁回收時，OS 用 `sfence.vma`（struct fence virtual memory）指令顯式 invalidate 特定 VA 或全部 TLB。

## 4. 快取尋址架構 (VIPT / PIPT)

設定 Cache 的 Index 與 Tag 到底用 VA 還是 PA，決定了 TLB 與 L1 的互動時序：

### 4.1 PIPT（Physically Indexed, Physically Tagged）

- 流程：TLB 轉譯 VA→PA **之後**，才拿 PA 去索引 & 比對 L1。
- 優點：極單純、**無 alias 問題**（同一 PA 只有一個 Cache 位置）。
- 缺點：L1 存取「被卡在 TLB 轉譯後面」，Critical Path 拉長（TLB delay + Cache access delay）。

### 4.2 VIPT（Virtually Indexed, Physically Tagged）

- **關鍵洞察**：頁內 offset（VA[11:0]）**轉譯前後不變**！即 `PA[11:0] == VA[11:0]`。
- 因此若 **Cache 的 Index 只取 offset 內的位元**（Cache 大小 ≦ Page Size × Sets），就能**在 TLB 完成前先算 Index**：

```
     │ VA[11:0]
     ▼ Index 直接算 ──────► L1 (以 VA 索引)
TLB 轉譯 VA→PA ──────────► Tag 比對（PA 的 Tag 部分）◄ 與 L1 平行完成
```

- 時間上兩條路並行 → **L1 存取 + TLB 轉譯同時進行**，命中總延遲只受較慢者主導。
- **Aliasing（同義字）問題**：兩個不同的 VA 可能對映到同一 PA —— 若 L1 內同時存在兩份 copy 就衝突。解法：
  - 強制 Index 落在 offset 內（限制 L1 大小為 < PageSize × assoc）；
  - 偵測到 alias 時 invalidate/merge；
  - 頁對齊容許 1:1 的 VA→PA 對映避免 aliasing。

> 權衡總結：PIPT 較安全但慢；VIPT 較快但受限。**現代 L1 幾乎都是 VIPT**——把 offset 當 index，並保持 L1 ≤ 4KB × Ways 以便 Index 全落在 offset 內，避開 alias 真相。

### 4.3 其他設計：VIVT（完全虛擬）與 Related

完全用 VA（VIVT）確實無 TLB 依賴，但同一 PA 存在多份 copy 的 aliasing & 一致性災難，**現代不做**，僅在頁面保含（page coloring）研究出現。

## 5. 組合範例：一次 load 的完整流程

```
CPU 要求 load [VA=0x...8123]
  1. TLB 查 (VA VPN) ──────────────────────────────┐ (miss)
  2. (hit) TLB → PA=PATABLE+PFN ─────► VIPT L1 比對
  3. 硬體 Page Walker：走 Sv39 三層表 ──► PTE    │
  4. 取得 PA，填充 TLB                               ▼
  5. 重試 load ────► L1 hit (資料在此) 或 L2/DRAM fetch
```

- L1 miss + L2 hit：AMAT ≈ TLB hit + L1 miss ratio×L2 latency。
- L1 + L2 都 miss：走向 DRAM，含 Page Walk……現代 CPU 的 walker 有自己的 caching 結構。

---

## 6. 小結

- VM = 隔離 + 抽象 + 無界（swap）。
- 多層頁表以稀疏分配省空間，三層（Sv39）是 RV64 版本。
- Page Fault 靠 OS 載入 PTE 後重試。
- TLB 讓轉譯成本降到 cache-hit 級；ASID 讓 context switch 不必全清。
- L1 主流 VIPT：Index 用 VA 低位（=PA offset），Tag 用 PA，平行查詢。

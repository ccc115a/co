## 1. 從單循環到流水線

### 1.1 為什麼需要流水線？

單循環（Single-Cycle）設計在一個 Clock Cycle 內完成整條指令：Fetch → Decode → Execute → Memory → WriteBack。好處是邏輯簡單，壞處是**所有硬體都只被使用週期的極小部分**：

- ALU 只在執行階段工作了幾奈秒，其餘時間閒置；
- 記憶體（I-Cache/D-Cache）在同一個 cycle 被兩次存取，根本不可能實現；
- Clock Cycle 必須以**最慢路徑**（通常是最耗時的一條指令）為準，例如 load（要依序經過完整資料路徑）。

因此單循環設計的 CPI（Cycles Per Instruction）= 1，但 Clock Rate 卻被拖到只有 1 GHz 左右。

**流水線（Pipeline）** 的哲學與洗衣房完全一致：把指令拆成多個階段，各階段硬體**同時**各自處理不同指令。理想情況下吞吐量（Throughput）每 cycle 完成一條指令，且 Clock Rate 只由**最慢單一階段**決定（如 2 ns × 5 階段 → 500 MHz 也行）。

> 關鍵權衡：流水線提升的是**吞吐量（Throughput）**，不是**延遲（Latency）**。單一指令仍要花約 5 個 cycle 才能完成（假設各階段 1 cycle），只是好幾條指令同時在管線裡前進。

### 1.2 五個階段的拆解

| 階段 | 縮寫 | 職責 | 主要硬體 |
|------|------|------|----------|
| **Instruction Fetch** | IF | 依 PC 從 I-Cache 讀取指令；更新 `PC = PC + 4` | I-Cache、PC 暫存器、加法器 |
| **Instruction Decode** | ID | Parse 指令；**平行讀取暫存器檔** `rs1`/`rs2`；Sign-Extend 立即數 | Register File、解碼電路、Imm Gen |
| **Execute** | EX | ALU 計算算術結果；計算 Load/Store 位址；判斷 Branch 是否成立 | ALU、Forwarding Mux |
| **Memory Access** | MEM | 依 `MemRead`/`MemWrite` 控制訊號存取 D-Cache | D-Cache |
| **Write Back** | WB | 將 ALU 結果或 D-Cache 讀值寫回 Register File (`rd`) | Register File（寫入埠） |

流水線階段之間以**管線暫存器（Pipeline Registers）** 分隔：`IF/ID`、`ID/EX`、`EX/MEM`、`MEM/WB`。這些暫存器同時扮演「傳送帶」的角色——每個 cycle 結束時，把本階段的資料與控制訊號拍（Latch）到下一階段。

## 2. 資料路徑與控制訊號

### 2.1 資料路徑圖

RISC-V 五階段資料路徑（含後續會加入的 Forwarding 與 Hazard Unit 位置）：

```
              ┌────────────────────────────────────────────────────────────────────────┐
              │                                                                        │
              ▼ I-Cache                                     ┌────────── Data ─────────┐│
  PC ──►[IF]─┼─► IF/ID ──►[ID]─┬─► ID/EX ──►[EX] ──► EX/MEM ─►[MEM] ─► MEM/WB ───►[WB]─┘│
    │    instr                 │           │                    │                      │
    │    (控制訊號 ID/EX)       │           │                    │                      │
    ▼                          ▼           ▼                    ▼                      │
 [PC+4] ───────────────────────────────────────────────────────────────────────────────┘
```

控制訊號表（由 decode 產生，隨指令一路往下走水管）：

| 控制訊號 | 值 | 受影響階段 |
|----------|-----|-----------|
| `RegWrite` | 是否寫回 Register File | WB |
| `MemToReg` | WB 來源選 ALU result 或 Memory data | WB |
| `MemRead` / `MemWrite` | D-Cache 讀 / 寫致能 | MEM |
| `Branch` | 是否為 Branch 指令（且 ALU zero 成立） | EX→IF |
| `ALUSrc` | ALU 來源 2：暫存器 or Imm | EX |
| `ALUOp` / `funct` 子解碼 | 決定 ALU 操作 | EX |

### 2.2 時序範例：instruction stream 的推進

| Cycle | IF | ID | EX | MEM | WB |
|-------|----|----|----|----|----|
| 1 | ¥ 1 (lw) | | | | |
| 2 | 2 (add) | 1 (lw) | | | |
| 3 | 3 (sw) | 2 (add) | 1 (lw) | | |
| 4 | 4 | 3 (sw) | 2 (add) | 1 (lw) | |
| 5 | 5 | 4 | 3 (sw) | 2 (add) | 1 (lw) |
| 6 | 6 | 5 | 4 | 3 (sw) | 2 (add) |

理想管線每 cycle 完成一條指令，含 overhead 後 CPI ≈ 1/(1 + pipeline overhead)。

## 3. 資料冒險 (Data Hazards) 與前遞 (Forwarding)

### 3.1 冒險的三種基本型態

| 冒險 | 全名 | 發生情況 | 可否 Forwarding 解決 |
|------|------|----------|---------------------|
| **RAW** | Read-After-Write | 後讀指令需要**前寫指令的結果** | ✅ 是（除 Load-Use） |
| **WAR** | Write-After-Read | 後寫指令覆寫前讀指令將要讀的暫存器 | 亂序執行才出現（1.4） |
| **WAW** | Write-After-Write | 兩條指令寫同一暫存器，順序被顛倒 | 亂序執行才出現（1.4） |

在**五階段按序流水線**中，指令一定是依序發射的（register read 在 ID 階段固定比後指令早），所以 WAR/WAW 不可能出現。真正的問題是 RAW——後續指令所需的資料，在它進入 EX 階段時，前面那條指令**還沒把結果寫進 Register File**。

### 3.2 RAW 衝突的典型例子

```asm
add  x1, x2, x3   # 1. 在 EX/MEM 後才得到結果，WB 才寫入 x1
sub  x4, x1, x5   # 2. ID 階段讀 x1 → 但 x1 還是舊值!  ← 衝突
and  x6, x1, x7   # 3. ID 階段讀 x1 → 仍是舊值
or   x8, x1, x9   # 4. ID 階段讀 x1 → 也是舊值
xor  x10, x1, x11 # 5. 此時 WB 剛寫入 x1，無衝突
```

時序（✗ = 讀到舊值，✓ = 前遞）：

| Cycle | 1 | 2 | 3 | 4 | 5 |
|-------|---|---|---|---|---|
| add | IF | ID | EX | MEM | WB |
| sub | | IF | ID ✗ | EX | |
| and | | | IF | ID ✗ | |

- `sub` 需要在 cycle 4 的 EX 階段用 `x1`，但 `add` 要 cycle 5（WB）才寫入。
- **First Solution（悲觀）**：Stall 兩條指令直到 add 寫完——正確但效能大減。

### 3.3 Forwarding (Bypass) 的關鍵洞察

> 其實資料**早就存在**了！`add` 在 cycle 3 的 EX 階段就算出了 ALUResult。

既然如此，硬體可以在暫存器檔還沒更新前，**直接把 ALUResult 從 EX/MEM（或 MEM/WB）水管暫存器「抄近路」送回 EX 階段的 ALU 輸入端**。這就是 **Forwarding / Bypassing**：

```
              EX/MEM                    MEM/WB
               │  ALUResult               │  WriteData
               ▼                          ▼
          ┌───────────┐            ┌───────────┐
rs1 ─────►│ Forwarding │───────►   │ Forwarding │───► Mux ──► ALU input 1
rs2 ─────►│  Mux (A)   │           │  Mux (B)   │───► Mux ──► ALU input 2
          └───────────┘            └───────────┘
              ▲sel                     ▲sel
              │                        │
         Hazard / Forwarding Unit（看 Ex/Mem.rd、Mem/WB.rd）
```

**Forwarding 條件**（EX 階段 ALU 來源選用邏輯）：

```
# 若 ID/EX 所寫暫存器 == 前方指令的目標暫存器
若 EX/MEM.RegWrite == 1 且 EX/MEM.rd != x0 且 EX/MEM.rd == ID/EX.rs1
    → ForwardA = 10（ALU 來源 1 = EX/MEM.ALUResult）

若 MEM/WB.RegWrite == 1 且 MEM/WB.rd != x0 且 MEM/WB.rd == ID/EX.rs1
    → ForwardA = 01（ALU 來源 1 = MEM/WB 的資料）

同理可套用於 rs2（ForwardB）
```

加上 Forwarding 後，`add`/`sub` 的衝突消失，CPI 回到 1。**唯一的例外是 Load-Use Hazard**。

### 3.4 Load-Use Hazard：必須 Stall

Load 的資料要到 cycle 5（MEM/WB，讀出 D-Cache）那一刻才真正存在。如果下條指令在**緊接著的 EX 階段**就要用它（`lw x1, 0(x2)` 之後馬上 `sub x4, x1, x5`），則任何 forwarding 都來不及——**必須插一個 bubble**。

```
Cycle     1    2    3    4    5
lw x1 —  IF    ID    EX    MEM   WB
sub      IF    ID    EX    ...（stall 1 cycle → 再 forward）
                    STALL
add x2 — IF    ID    動手算    ...
（下條） IF後續→ bubble 注入
```

**Hazard Unit 偵測條件**（在 ID 階段）：

```
若 ID/EX.MemRead == 1                       # 前方是 load
   且 (ID/EX.rd == IF/ID.rs1 || ID/EX.rd == IF/ID.rs2)
   → issue STALL
```

**Stall 的三步動作（同一個 cycle 完成）**：

1. **凍結 PC 暫存器**：`PCEnable = 0`，下 cycle 仍 fetch 同一條指令。
2. **凍結 IF/ID 管線暫存器**：讓下一條指令重複讀一次（`IF/IDWrite = 0`）。
3. **注入 Bubble**：把 ID/EX 的控制訊號全部清零（寫入 NOP），空出 EX 階段執行權。

> **為何不直接朝 MEM→EX 做 forwarding？** 因為 MEM/WB 的資料要等 Store/Load 在 MEM 階段結束才更新；而 load 的下一條指令在**同時刻**（EX 階段）就想要——時間上永遠差了「一個全 cycle」。（有些設計會對 load-to-use 距離為 1 的情況做「雙重 forwarding + 減半 stall」，但標準五階段管線就是 1-cycle stall。）

## 4. 控制冒險 (Control Hazards) 與 Flush

### 4.1 Branch 帶來的控制冒險

Branch（如 `beq`）的成立與否直到 **EX 階段**才被 ALU 判定（比較 `rs1`、`rs2` + 算 target）。但在 IF/ID 取得 branch 指令的下一個 cycle，管線就**盲目地** fetch 了 PC+4——若 branch 成立，這條後續指令根本不該執行。

解決方式有兩大類：**Stall（等著確認）** 與 **Predict（猜測）**。本節談基礎解法；1.3 節談動態預測。

### 4.2 基本解法：Stall 直到確定

最保守做法：遇到 Branch 指令就停下 2 個 cycle，等 EX 階段確認結果後再決定下條指令位址。效能損失巨大（每個 branch 約損失 ~2 cycle，而 branch 約佔全部指令 15%-20%）。

```
Cycle     1    2    3    4    5
beq     IF    ID    EX (確認)
next ✗  IF    IF    (被 stall，不執行) ... 
後續    ─    bubble  bubble  IF    ID  （真正要跳的目標）
```

### 4.3 主流做法：預測 Not-Taken + 錯誤時 Flush

1. 假設 branch **不成立**：IF 直接 fetch `PC+4`（不用等），零延遲。
2. 到 EX 階段若發現 Branch 成立且預測錯誤：
   - **Flush**：把一條或多條已錯誤 fetch 的指令（IF/ID、ID/EX 管線暫存器）清空為 NOP；
   - 同時把 PC 更新為 Branch Target，這一 cycle 之後從正確位址開始取指。

```
Cycle     1    2    3    4
beq     IF    ID    EX (確認成立)
next ✗  IF    ID    FLUSH (被刷掉)
target  ─    ─    IF    ID    EX ...（正確路徑）
```

**Flush 的硬體實作**：在 IF/ID 與 ID/EX 管線暫存器上加入「Clear」輸入，來自 Branch 確認訊號 `BranchMisPredict`。被清零的指令在後續階段被當作 NOP 執行，其副作用（寫暫存器、訪存）全被取消。

### 4.4 兩難：Branch 判定拖到 EX 階段的代價

- 若 Branch 在 EX 階段確認，錯誤路徑損失 **2 cycles**（pipe 中兩條指令被 flush）。
- 把 Branch 判定提早到 ID 階段（用專用比較暫存器而非等 ALU）可以把損失降到 **1 cycle**——這是許多實作（如經典 RISC-V pipelined core）採用的最佳化。

**預測準確率的重要性**：假設 Branch 佔 20%、預測失準率為 10%（即 2% 的指令會誤判），mis-prediction penalty 為 2 cycles，則整體 CPI 損失 = 0.02 × 2 = +0.04 CPI（理想為 1）。若完全沒預測（每次 stall 2 cycles），損失 = 0.2 × 2 = 0.4 CPI，差距 10 倍。這正是 1.3 節動態分支預測器存在的理由。

## 5. 實作範例：Verilog 摘要

以下片段展示 Forwarding 與 Hazard Unit 的核心邏輯（簡化）：

```verilog
// ---------- Forwarding Unit ----------
always @(*) begin
  if (ex_mem_regwrite && (ex_mem_rd != 0) && (ex_mem_rd == id_ex_rs1))
    forwardA = 2'b10;            // 來源：EX/MEM.ALUResult
  else if (mem_wb_regwrite && (mem_wb_rd != 0) && (mem_wb_rd == id_ex_rs1))
    forwardA = 2'b01;            // 來源：MEM/WB
  else
    forwardA = 2'b00;            // 來源：Register File
end

// ---------- Hazard Unit (Load-Use) ----------
wire stall = id_ex_memread
          && (id_ex_rd == if_id_rs1 || id_ex_rd == if_id_rs2);

// ---------- Stage Control ----------
assign PC_next    = (branch_taken) ? branch_target : (stall ? PC : PC + 4);
assign IFID_write = ~stall;        // 凍結 IF/ID
assign IDEX_ctrl  = stall ? 9'b0 : id_control_signals;  // 注入 bubble

// ---------- Redirect (Control Hazard, branch resolved in EX) ----------
wire branch_mispred = (id_ex_branch && (alu_zero != predicted_taken));
// sel 使 IF/ID、ID/EX 的內容在 EX 確認 mispredict 時被 flush 成 NOP
```

（完整可模擬的管線核心可參考 `code/計算機結構/` 下的 RISC-V 專案。）

## 6. 效能統計：理想 vs 真實

| 指標 | 理想管線 | 真實管線（含冒險） |
|------|----------|---------------------|
| CPI | 1.0 | ~1.1–1.5 |
| 單條指令延遲 | ~5 cycles | ~5 cycles（不變） |
| Throughput | 每 cycle 1 條指令 | 低於 1（平均） |
| 造成因素 | — | Load-Use stall、Branch mispredict、struct hazard（記憶體存取衝突）、data hazard 未被 forward 之處 |

---

## 7. 小結與延伸

- 五階段管線 = IF/ID/EX/MEM/WB，分隔管線暫存器扮演傳送帶。
- RAW 冒險靠 **Forwarding** 化解，只有 Load-Use 需要 **Stall + Bubble**。
- Branch 冒險靠 **猜測 Not-Taken + Flush** 處理，錯一次損失 2 cycles。
- 這些技巧都是為了逼近「每 cycle 一條指令」的吞吐量理想值。

下一節（1.3）將深入動態分支預測：BTB、2-bit 飽和計數器與 2-Level 預測器，把 Branch 的代價從 2 cycles 壓低到接近 0。

## 1. 從單發射到多發射

### 1.1 為什麼一個 Cycle 一條指令不夠？

回顧 1.2 的理想管線：CPI = 1。但現代 CPU 渴望 CPI < 1，亦即**每個 cycle 完成超過一條指令**。這需要：

- **Fetch 寬度**：一次取多條指令（4-way fetch）。
- **Decode 寬度**：一次解碼多條。
- **Issue 寬度**：一次把多條指令送往多個執行單元。
- **多個 Functional Unit（FU）**：多個 ALU / 多格位址單元 / 浮點運算器，各自獨立。

這個「**多發射**」概念即是 **Superscalar**。配合 **IPC（Instructions Per Clock）** 指標：

$$
IPC = \frac{\text{執行的指令數}}{\text{週期數}} = \frac{1}{CPI}
$$

理想 4-way superscalar 的 IPC 上限為 4，但受制於資料依賴、功能單元數量、Fetch 瓶頸與前端的 misprediction。

### 1.2 兩種流派

| 流派 | 執行方式 | 代表作 |
|------|----------|--------|
| **In-Order Superscalar** | 按程式順序發射並進入執行單元；遇到長延遲指令就整條截停 | 早期 Pentium、ARM Cortex-A53 |
| **Out-of-Order (OoO)** | 硬體自由調度，先準備好的指令先執行 | 主流高性能核心（Cortex-A77、Zen、Golden Cove） |

**亂序執行的核心洞察**：程式中的指令**不必照順序執行**，只要能保證「結果與按序執行相同」即可。

```asm
lw   x1, 0(x2)     # ※ 高延遲：等待記憶體（可能 100+ cycles）
add  x4, x5, x6    # 1. 不依賴 x1，可先算！
mul  x7, x8, x9    # 2. 也不依賴，可先算！
add  x10, x1, x11  # 3. 依賴 x1，得等 load 完成
```

在按序管線中，第 1 條 load 卡住會讓後面 3 條全部停擺；在 OoO 中，CPU 會讓 `add` 與 `mul` **偷偷往前溜**，等 load 資料回填後再算 `add x10...`，總執行時間大幅縮短。

## 2. Tomasulo 演算法：資料依賴解耦的基石

Tomasulo（1967，發明於 IBM System/360 Model 91）是第一個**資料流（Dataflow）+ 亂序**的實作思想，現代 OoO 幾乎都是其變體。

### 2.1 核心結構：Reservation Stations (RS)

每一類 Functional Unit（ALU、浮點、Load/Store）前方配一個 **Reservation Station 佇列**（也被稱為「issue queue」）。RS entry 含：

```
| Ready 位元 | 指令類別 | 操作 | Vj | Vk   | Qj | Qk      | Result(可選) |
|-----------|----------|------|----|----|----|---------|-------------|
| 是否已就緒 | ADD/MUL.. | op  | 值 | 值 | 等待的 RS 編號 | 預測/已算結果 |
| (Broadcast 後清成 ready) |
```

- `Vj/Vk`：**已經就緒（available）的運算元數值**。
- `Qj/Qk`：若運算元尚未就緒，則記錄「生產者」的 RS 編號或來源單位編號。

### 2.2 三階段運作流程

#### Issue（發射）

1. 自 Instruction Queue（IQ）取依序的指令。
2. **佔用**一個空閒 RS entry（若 RS 已滿，前端 stall）。
3. 讀取 Register File 中現有的運算元數值填入 `Vj/Vk`；若來源暫存器正被升級器登記為「等待生產」，則在 `Qj/Qk` 記下生產者編號。

#### Execute（執行）

- 當 entry 的所有運算元變為 Ready（`Q` 均 NULL、`V` 都有效）時，**就可開始執行**——不要求程式順序。
- 多個 RS 同時就緒時，由硬體挑（考量優先權、延遲、可執行次數）。
- Execution 完成：結果送達自己這類單元的專屬 Buffer（或直接往 CDB 廣播）。

#### Write Result（寫結果）

- 結果**廣播到 Common Data Bus (CDB)**（連接著所有 RS 與 Register File）。
- 每個 RS 監聽 CDB：若運算元依賴的生產者編號被廣播填滿（`Qj == broadcasted tag`），就抓下數值並把 RS 標成 Ready。
- Register File 也監聽：若是自己等待的來源，則更新對應架構暫存器的「已算結果」。

### 2.3 Tomasulo 解決了什麼？

- **自動 Forwarding**：CDB 廣播等於全域 bypass，不需像五階段管線額外建 forwarding 邏輯。
- **消除 WAR/WAW（偽依賴）**：這是下一節 Register Renaming 的雛形——RS 以「資料流」而非「程式順序」連結，只要後續讀者已 READY，先寫後讀者不會互卡。

```verilog
// Tomasulo 核心讀取的抽象（簡化）
module reservation_station(
  input [DATA-1:0] cdb_value, input [TAG-1:0] cdb_tag, input cdb_valid,
  inout reg [DATA-1:0] vj, vk, inout reg [TAG-1:0] qj, qk
);
  always @(posedge clk) begin
    if (cdb_valid) begin
      if (qj == cdb_tag) begin vj <= cdb_value; qj <= NULL; end
      if (qk == cdb_tag) begin vk <= cdb_value; qk <= NULL; end
    end
  end
endmodule
```

## 3. 暫存器重新命名 (Register Renaming) 與偽依賴

### 3.1 偽依賴（False Dependency）是什麼？

考慮：

```asm
add  x5, x6, x7     # 讀 x6,x7 寫 x5
lw   x1, 0(x2)      # 長延遲
sub  x5, x8, x9     # ← 又寫 x5！與前面的 add 產生 WAW 疑似依賴
addi x3, x5, 1      # ← 讀 x5：與 sub 產生 RAW 依賴
```

問題出在：**ISA 只有 32 個架構暫存器（Architectural Registers）**，程式二次使用同一暫存器名稱，但其實**兩條 add/sub 的資料完全無關**。硬體卻不敢把它們並行或重排，深怕後者寫入會覆蓋前者——這是**偽依賴 WAR/WAW**。

### 3.2 動態映射到物理暫存器

**Register Renaming**：把 32 個 ISA 暫存器對應到更多**物理暫存器（Physical Registers）**，例如 160 個。採用 **RAT（Register Alias Table）**：

```
架構暫存器 x5 ──► RAT ──► 物理暫存器 P40 (目前存的 value)
                       〔pending 時：等待生產者 P83〕
```

發射時：

1. 為目標架構暫存器（如 `x5`）**分配一個新的物理暫存器**（如 P83）。
2. RAT 記錄 `x5 → P83`。
3. 來源（如 `x6`）讀取時，用 RAT 查「目前 x6 對應的物理暫存器 P92」。
4. 當 P83 被算完寫入，x5 就自然指向新的值。

如此 **WAW 消失**：`add x5...` 寫 P83、`sub x5...` 寫 P84，兩個寫目標不同物理暫存器，互相獨立。
**WAR 消失**：`sub x5...`（讀 x8,x9）在 RAT 更新為 `x5→P84` 之前，舊讀者早已用 P83 讀值；`addi x3, x5, 1` 讀 P84。

### 3.3 關鍵：何時真的能「退休」

架構暫存器只該有一份最終值。當指令**依序提交（commit）**時，RAT 才正式切到該指令的物理暫存器。之前的所有 P 都是「投機（speculative）」資料，若被 flush（如 branch mispredict）則全部退回，RAT 還原成前一時刻的 snapshot。

### 3.4 Physical Register File（PRF）

物理暫存器數多於架構暫存器（如 160:32）。注意 **RAT 的查詢與分配是重疊的 bottleneck**——給定寬 4 的發射，每個 cycle 要同時查 4 個來源、分配 4 個新目標。這是現代後端最壅擠的電路之一。

## 4. 重排序緩衝區 (ROB)：亂序執行、順序提交

### 4.1 為何需要 ROB？

**Precise Exception**（精確例外）是 System Software 的鐵律：當例外發生時，硬體必須能還原「恰在該指令之前的架構狀態」，讓 OS 重新處置後能重啟執行。但亂序執行弄亂了完成的順序——若直接寫入架構暫存器，就無法還原。因此：

> 亂序執行（Out-of-Order Execute），但**順序提交（In-Order Commit）**。

**ROB（Reorder Buffer）** 是達成此目標的 FIFO 佇列，每個 entry 記錄：

```
| 指令 | 是否完成 (Ready) | 目的暫存器(物理) | 例外資訊 | 分支預測標記 |
|<seq> |                 | 寫回 PRF 的標記 | 若有     | 預測失敗要 flush |
```

### 4.2 流水流程

1. **分配（Allocate）**：發射時依程式順序在 ROB 尾端插入 entry（RAT 同步更新）。
2. **執行完成**：結果寫入**物理暫存器檔（PRF）**（不是架構暫存器檔），ROB entry 標注 Ready + 記錄目的 PRF。
3. **提交（Commit）**：當 **ROB 最頂端（head）** 那條指令確定（無例外、無 mispredict、已完成）時：
   - 若為寫入指令，把 PRF 的值正式提交至 Architectural Register File（或直接更新 RAT，確保架構視圖正確）；
   - 移除 head，指標前進。
4. **例外/預測失敗**：flush 掉 ROB 中所有「在該指令之後」的 entries，RAT 回滾至該指令之前的快照，`mepc/scause` 設妥並跳轉 handler。

### 4.3 ROB 與 Physical File 的分工

```
                       Queue
  Instruction Stream ─► [Decode] ─► [Rename) ─► [ROB 分配 + RS 發射]
                                          │
                                    [Execute]  ◄─ CDB 廣播
                                          │
                                    [PRF 寫入]  ──► 完成
                                          │
                                    [Commit 檢查 head] ─► 架構視圖
```

- **ROB 只管「順序與例外」**；**RS 只管「資料流調度」**——兩者合一，正是現代 OoO 的架構輪廓（Intel P6、ARM Cortex-A 系列、AMD Zen 皆屬此類）。

## 5. 效能分析與硬體代價

### 5.1 ILP 量化

理想的 IPC = 發射寬度；真實 IPC 受制於：

1. **依賴鏈（Dependency Chain）**：`a→b→c→d` 的串聯延遲（critical path）無法靠亂序縮短。
2. **功能單元不足**：指令可並行但 FU 數量有限 → 出現「resource stall」。
3. **發射佇列寬度/深度**：ROB、RS 的 size 決定了可探索的 OoO 視窗。
4. **記憶體延遲**：Cache miss 時 load queue 的長度影響可重排範圍。
5. **前端限制**：Fetch 寬度、分支預測失準（1.3 節）直接砍 IPC。

典型數字：4-wide OoO（ROB ~192 entries）在 SPECint 上 IPC ≈ 1.5–2.5（遠低於理論的 4）。**Amdahl 在架構上的反方向**——ILP 邊際報酬遞減，這就是為何現代 CPU 轉向多核心 + SMT + 更多 FU。

### 5.2 SMT（Simultaneous Multi-Threading）簡介

即使 4-wide，一個執行緒的依賴鏈也常讓 FU 閒置。**SMT**讓多個「硬體執行緒」共用同一組 OoO 引擎，各自獨立 RAT/ROB 的一部分，填滿空閒槽位。Intel HT（2-way）、Zen（2-way）、Apple Firestorm（2-way）皆此。

### 5.3 功耗與矽成本

OoO 消耗的電晶體主要花在：PRF（物理暫存器檔）、RS 內容、RAT（多埠）、ROB 內容、Mux 網路、存取優先權電路。**OoO 的 power/area 約是按序核的 2-4 倍以上**——這是嵌入式/行動裝置選用 In-Order（如 Cortex-A53、RISC-V 小型核心）或淺 OoO 的原因。

## 6. 小結

- **Superscalar**：多發射 + 多 FU，追求 IPC > 1。
- **Tomasulo**：RS + CDB 廣播，資料流驅動亂序執行。
- **Renaming**：RAT 把 32 個 ISA 暫存器對映到更多物理暫存器，消滅 WAR/WAW 偽依賴。
- **ROB**：亂序執行+順序提交，確保 Precise Exception、支援 misprediction 回滾。
- 極限：ILP 收益遞減 → 轉向多核心、SMT、DLP/向量（第三章）。

下一章我們把視角從指令層**轉到記憶體層**：Cache、虛擬記憶體、DRAM 與匯流排——那才是現代 CPU 最常卡住的「Memory Wall」。
